# M1 Git とブランチの基本

所要時間の目安: 準備 30 分 ＋ 説明 25 分 ＋ 演習 105 分

> **このモジュールでも、コードは書きません。** 練習に使うのは、`practice/diary.md` という、**短い日記のファイル**だけです。手順書にある 1 行を足したり、消したりしながら、**Git という道具の使い方に慣れる**ことが目的です。

## 1. Git とは

Git は、**ファイルの変更の履歴を残し、安全に試し、他の人と作業を合わせるための道具**です。

| 困りごと | Git があると |
|---|---|
| 変更したら、元に戻せなくなった | 履歴から、前の状態に戻せる |
| 試しに変更したいが、壊すのが怖い | **別の作業の流れ（ブランチ）**で試し、気に入らなければ捨てられる |
| 複数の人が、同じファイルを変更したい | 変更を、あとから合わせられる（PR。M4） |
| 誰が、いつ、何を、なぜ変えたか分からない | 履歴に、変更ごとのメモが残る |

## 2. 用語

| 用語 | 意味 | たとえ |
|---|---|---|
| **リポジトリ** | ファイルと、その変更の**履歴**をまとめて入れた場所 | プロジェクトのフォルダ ＋ 履歴の記録 |
| **コミット** | **変更のまとまりを、1 つの記録として残す**こと、またはその記録 | セーブポイント |
| **ブランチ** | 履歴の、**別の流れ**。`main` が、正とする流れ | 作業用の、別のノート |
| **リモート（`origin`）** | GitHub の上にある、リポジトリの**コピー** | 共有のクラウド |
| **クローン** | GitHub のリポジトリを、自分のパソコンに**まるごとコピー**すること | — |
| **プッシュ（push）** | 自分のコミットを、GitHub に**送る**こと | クラウドへ保存 |
| **プル（pull）** | GitHub の新しい内容を、自分のパソコンに**取り込む**こと | クラウドから受け取る |

### 変更が記録されるまでの流れ

```
 作業フォルダ        ステージ        自分のパソコンの履歴        GitHub（origin）
 （ファイルを編集） ─ add ─▶ （記録する変更を選ぶ） ─ commit ─▶ （コミットが増える） ─ push ─▶ （共有される）
```

- **add**: 「次のコミットに、この変更を入れます」と選ぶ。
- **commit**: 選んだ変更を、**メモ（コミットメッセージ）つきで記録**する。まだ、自分のパソコンの中だけ。
- **push**: 記録を、GitHub に送る。ここで初めて、他の人に見える。

## 3. 準備（一度だけ）

### 3-1. 名前とメールアドレスを設定する

コミットには、**名前とメールアドレスが記録されます**。自分のターミナルで、次を実行します。

```bash
git config --global user.name "あなたの名前（ニックネームでもよい）"
git config --global user.email "メールアドレス"
```

> **メールアドレスは、GitHub の「noreply」アドレスをおすすめします。** コミットの記録は、公開される場合があるからです。GitHub の Settings → Emails に、「Keep my email addresses private」の設定と、`...@users.noreply.github.com` という形のアドレスが表示されます（画面の表記は、変わることがあります。分からなければ、講師に聞いてください）。

### 3-2. 自分のリポジトリを、クローンする

1. GitHub で、**自分のリポジトリ**（テンプレートから作ったもの）を開く。
2. 緑の「**Code**」ボタンを押し、「HTTPS」の URL をコピーする。
3. 自分のターミナルで、次を実行する（`<URL>` は、コピーした URL）。

   ```bash
   git clone <URL>
   cd <クローンされたフォルダ>
   ```

### 3-3. GitHub への認証

- クローンや push のときに、**ブラウザで GitHub にサインインする画面**が出る場合があります（Windows の Git に含まれる、認証の仕組みです）。画面の指示に従って、サインインします。
- **パスワードの入力を求められた場合、GitHub のパスワードは使えません。入力せず、講師に相談してください。**
- パスワードやトークンを、**チャットや AI に貼らない**でください（[M0](../m0-orientation/README.md)）。

> 認証の画面は、環境によって違います。この手順書の作成環境では、認証の画面は確認していません。うまくいかないときは、「ここまでは分かります、ここから分かりません」の形で、講師に伝えてください。

### 3-4. 動作の確認

クローンしたフォルダで、次を実行します。

```bash
git status
```

「`On branch main`」と「`nothing to commit, working tree clean`」が表示されれば、準備は完了です。

## 4. 読む（読むだけのコマンド）

次の 4 つは、**何も変更しません**（安全です）。いつ実行しても構いません。

| コマンド | 分かること |
|---|---|
| `git status` | 今いる**ブランチ**と、**変更の状況**（変更したファイル、記録待ちのファイル）。**迷ったら、まず、これ** |
| `git diff` | **何を、どう変えたか**（足した行は `+`、消した行は `-`）。まだ add していない変更 |
| `git log --oneline` | **コミットの履歴**（新しいものが上）。1 行ずつ、短く表示 |
| `git branch` | ブランチの一覧。`*` が、今いるブランチ |

> `git branch -a` は、GitHub 上のブランチ（`remotes/origin/…`）も表示します。

## 5. 記録する（ブランチを作って、変更を残す）

| 手順 | コマンド | 意味 |
|---|---|---|
| 1 | `git switch -c practice/名前` | **新しいブランチを作って、移る**（`-c` は create）。`main` を、直接変更しないため |
| 2 | （エディタでファイルを編集する） | 変更する |
| 3 | `git status` | 変更されたファイルを確認 |
| 4 | `git add <ファイル>` | 記録する変更を選ぶ |
| 5 | `git commit -m "メモ"` | **記録する**（メモは、何をしたかが分かる短い文） |
| 6 | `git push -u origin practice/名前` | GitHub に送る（`-u` は、最初の 1 回だけ） |
| 7 | `git switch main` | `main` に戻る |

- **`main` に、直接コミットしません**（M4 で、理由を学びます）。変更は、**ブランチ**で行います。
- コミットメッセージは、**あとで読む人（自分を含む）**のために、**何をしたか**が分かるように書きます。

## 6. 戻す（安全なものと、危険なもの）

| 操作 | コマンド | 何が起きるか | 安全度 |
|---|---|---|---|
| 未コミットの変更を、**捨てる** | `git restore <ファイル>` | **その変更は消える。取り消せない** | ⚠ 注意（捨ててよいと確かめてから） |
| コミットを、**打ち消す** | `git revert HEAD --no-edit` | **「打ち消す」という新しいコミット**が増える。履歴は残る | ✅ 安全 |
| 作業を、まるごと**巻き戻す** | `git reset --hard` | 未コミットの変更と、コミットが**消える** | ❌ **危険** |
| 履歴を、**強制的に**上書きして送る | `git push --force` | 他の人の履歴を**上書き**する | ❌ **危険** |
| 未管理のファイルを、**消す** | `git clean -f` | 管理外のファイルが**消える** | ❌ **危険** |
| ブランチを、**強制的に**消す | `git branch -D <名前>` | マージされていなくても**消える** | ❌ **危険** |

- 「戻したい」ときは、**まず `git status` と `git log --oneline` で、今の状態を確かめます**。
- **危険なコマンドは、AI が提案しても、許可しません**（[M6](../m6-ai-control/README.md) の許可カード）。迷ったら、**消さずに、打ち消す（`revert`）**ほうを選びます。

## 7. 合わせる（マージ）と、コンフリクト

別々のブランチでの変更を、**1 つに合わせる**ことを、**マージ**と言います（GitHub では、PR を「マージ」するのが、これです）。

| 場合 | 結果 |
|---|---|
| 別々のブランチが、**別の行・別のファイル**を変更した | **自動で合わさる** |
| **同じ行**を、別々に変更した | **コンフリクト（衝突）**。Git は、どちらが正しいか**判断できない**ので、**人に決めてもらう** |

コンフリクトは、**失敗ではなく、チーム開発では普通に起きること**です。慌てずに、次の順で対応します。

| 手順 | 操作 |
|---|---|
| 1 | `git status` で、**どのファイルが**衝突しているか（`both modified`）を確かめる |
| 2 | そのファイルを開き、**印**を読む。`<<<<<<< HEAD` から `=======` までが**今いるブランチ**、`=======` から `>>>>>>>` までが**合わせようとしている側** |
| 3 | **両方の内容を理解して**、残す形に直す。**印の行は、すべて消す** |
| 4 | `git diff --check` で、印が残っていないことを確かめる |
| 5 | `git add <ファイル>` → `git commit --no-edit` で、解消を記録する |
| やめる | 途中でやめるときは、`git merge --abort`（合わせる前に戻る） |

- **どちらを残すかは、内容を理解して決めます。** 迷ったら、書いた人に聞きます。AI に頼む場合も、**結果を `git diff` で読み**、片方の変更が**黙って消えていない**かを確かめます。
- PR の画面で「競合している」と表示されるときも、同じ仕組みです（[M4](../m4-pr-and-ci/README.md) の 5 節）。

## 8. よくある表示

| 表示 | 意味と対処 |
|---|---|
| `warning: ... LF will be replaced by CRLF ...` | Windows で出る、**改行コードの警告**。**無害**なので、気にしなくてよい |
| `nothing to commit, working tree clean` | 変更がない、きれいな状態 |
| `Changes not staged for commit` | **変更したが、まだ add していない** |
| `Changes to be committed` | **add 済みで、コミット待ち** |
| `Your branch is up to date with 'origin/...'` | GitHub のブランチと、同じ |
| `CONFLICT (content): Merge conflict in ...` | **コンフリクト**。7 節の手順で、人が解消する |
| `You have unmerged paths` | 合わせている途中で、**解消が済んでいないファイル**がある |

分からない表示は、**そのまま、講師に見せる**か、M2 で学ぶ AI に、**自分の言葉で**質問します（秘密や個人情報が入っていないかを、確認してから貼る）。

## 9. Git と AI（先に知っておくこと）

- **AI に Git の操作を頼んでもよい**のですが、**頼まなくても、AI がコミットすることがあります**。結果は、**必ず自分で確かめます**（`git status`、`git diff`、`git log --oneline`）。
- AI が実行しようとする Git のコマンドは、**確認画面で読んで**から許可します。分からないコマンドは、許可しません。
- だから、**自分で、Git の基本が分かっている**ことが、AI を安全に使う土台になります（M2、M6 へ続きます）。
