# M1-4 の答えと解説

> 先に、自分の予想と観察を書き残してから読んでください。この手順（衝突、解消、`--abort`）は、教材の作成時に、使い捨てのリポジトリで実際に確かめています。

## 予想と結果

### ヒント

- Git は、**行ごと**に、変更を見ている。
- 「どちらが正しいか」は、Git には**判断できない**。

### 答え

| 問い | 答え |
|---|---|
| 同じ行を別々に書き換えて合わせると | **衝突（コンフリクト）**する。`CONFLICT (content): Merge conflict in ...` と表示され、ファイルに印（`<<<<<<<` など）が書き込まれる |
| 別の行を書き換えた場合 | **自動で合わさる**（衝突しない）。それぞれの変更が、両方残る |
| どちらを残すか | **Git は決めない**。人が、内容を理解して決める |

### 印の意味

```text
<<<<<<< HEAD
- 1行目: 夜の記録        ← 今いるブランチ（B）の内容
=======
- 1行目: 朝の記録        ← 合わせようとしている側（A）の内容
>>>>>>> practice/conflict-a
```

### 手順 6 の表示

- 解消して `git add` したあとの `git status` は、「`All conflicts fixed but you are still merging`」。
- `git commit --no-edit` で、**マージのコミット**ができる。`git log --oneline --graph` には、**2 本の流れが合流**する形（`*   ...Merge branch ...`）が出る。

### 手順 7: `--abort`

`git merge --abort` で、**合わせる前の状態に戻る**（`git status` がきれいになり、履歴も合わせる前のまま）。**衝突が大きすぎる、よく分からない**と思ったら、まず、これでやめてよい。

### 手順 8 の答え

- **印を消し忘れてコミット**すると、`<<<<<<<` などの行が、**そのままファイルに入る**（日記の中に、印が混ざる）。コードなら、**動かなくなる**。`git diff --check` で、残りを検出できる。
- **自動で合わさるとき**: 別の行、または別のファイルを変更したとき。
- **AI に解消してもらうとき**: AI は、**片方の変更を、黙って捨てる**ことがある。解消の結果を、**`git diff` で読み**、**両方の意図が残っているか**を確かめる。**印が残っていない**ことも確かめる。意味が分からない部分は、**書いた人に聞く**。

## 振り返りの答え

- **衝突が起きる理由**: 同じ場所に、**別々の変更**があり、どちらが正しいか、Git には**判断できない**から。自動で選ぶと、**誰かの変更が、黙って消える**。
- **最初に確かめること**: `git status` で、**どのファイルが**衝突しているか。次に、そのファイルを開いて、**両方の内容を読む**。

## 補足

- 実際の開発では、衝突は、**PR を出したあと、`main` が先に進んだ**ときによく起きる（M4 の 5 節）。
- 衝突は、**失敗ではなく、普通のこと**。慌てず、`status` を見て、必要なら `--abort` でやめて、落ち着いて、やり直せばよい。
- 衝突の解消では、**コミットメッセージの編集画面**が開くことがある（`--no-edit` を付けないとき）。その場合は、そのまま保存して閉じる。
