# M1 確認の質問の答えと解説

> 先に、自分の言葉で答えを考えてから読んでください。答えは 1 つではありません。

## 1. コミット、ブランチ、プッシュを、自分の言葉で説明できるか。

**答えの例**: **コミット**は、変更のまとまりを、メモつきで記録すること（セーブポイント）。**ブランチ**は、履歴の別の流れで、`main` に影響せずに、試せる作業用の場所。**プッシュ**は、自分のパソコンのコミットを、GitHub に送って、共有すること。

**押さえる点**
- コミットは、**自分のパソコンの中**の記録。プッシュして初めて、GitHub に届く。
- 図（作業フォルダ → add → commit → push）を、見ずに説明できる。

## 2. `git status` と `git diff` で、それぞれ何が分かるか。

**答えの例**: `git status` は、**今いるブランチ**と、**どのファイルが、どういう状態か**（変更した／add 済み／きれい）が分かる。`git diff` は、**中身の、どこが、どう変わったか**（`+` が足した行、`-` が消した行）が分かる。まず `status` で全体を見て、`diff` で詳しく見る。

**押さえる点**: どちらも**何も変更しない**ので、迷ったら、いつでも実行してよい。

## 3. 変更を記録して、GitHub に送るまでの流れを、順に説明できるか。

**答えの例**: ①ブランチを作る（`git switch -c`）→ ②ファイルを編集する → ③`git status` で確認 → ④`git add` で、記録する変更を選ぶ → ⑤`git commit -m` で記録する → ⑥`git push -u origin <ブランチ>` で、GitHub に送る。

**押さえる点**: `main` に直接ではなく、**ブランチ**で行う。コミットのメモは、何をしたかが分かるように書く。

## 4. `main` に直接変更せず、ブランチで作業するのは、なぜか。

**答えの例**: `main` は「正とする流れ」で、他の人も土台にするから。直接変更すると、**壊れた状態が、みんなに影響**する。ブランチなら、**失敗しても、捨てるだけ**で済み、気に入った変更だけを、PR を通して、`main` に合わせられる。

**押さえる点**: 「試しやすさ」と「他の人への影響の小ささ」の、両方を言える。

## 5. 安全に戻す方法と、危険なコマンドの違いは何か。`git revert` が安全なのは、なぜか。

**答えの例**: 安全な方法は、**履歴を残したまま**戻すもの（`git revert`: 打ち消しの、新しいコミットを作る）。危険なコマンド（`git reset --hard`、`git push --force`、`git clean -f`、`git branch -D`）は、**変更や履歴、ファイルを、消して、取り戻せなくする**。`revert` が安全なのは、**何も失わない**（元のコミットも、履歴に残る）から。

**押さえる点**
- `git restore` は、**コミットしていない変更を捨てる**ので、「注意」。
- 戻したいときは、**まず `git status` と `git log --oneline` で、状態を確かめる**。
- 危険なコマンドは、**AI が提案しても許可しない**。

## 6. AI が、頼んでいないコミットをしたとき、どう確かめるか。

**答えの例**: `git log --oneline`（`--all` を付けると、全ブランチ）で、**頼んでいないコミットが増えていないか**を見る。`git diff`（または、コミットの内容）で、**何が変わったか**を読む。範囲外の変更があれば、`git revert` で打ち消す（または、そのブランチごと捨てる）。AI が実行しようとする Git のコマンドは、**確認画面で読んで**から許可する。

**押さえる点**: AI は、頼んでいなくても、コミットすることがある（M6 の worktree の試験で、実際に確認した）。**結果は、自分の目で確かめる**。

## 7. コンフリクトとは何か。なぜ起きるか。起きたとき、どの順で対応するか。

**答えの例**: 別々のブランチが、**同じ行を別の内容に変更**したまま合わせようとしたとき、Git が**どちらが正しいか判断できず、人に決めてもらう**状態。自動で選ぶと、誰かの変更が黙って消えるから。対応は、**`git status` でどのファイルかを確かめる → ファイルを開き、印（`<<<<<<<`、`=======`、`>>>>>>>`）の両側を読む → 内容を理解して残す形に直し、印を消す → `git diff --check` で確認 → `git add` と `git commit` で記録**。やめるときは `git merge --abort`。

**押さえる点**
- 失敗ではなく、普通のこと。慌てず、まず `status`。
- 「どちらを残すか」は、内容を理解して**人が**決める。AI に任せる場合も、結果を `git diff` で読む。
- 印を消し忘れてコミットしない（`git diff --check`）。
