# M10 デプロイ

所要時間の目安: 準備 30 分 ＋ 説明 25 分 ＋ 演習 130 分

> **対象: L1（インフラ担当）**。そのほかの人は、**講師の実演を見て**、「確認」の問いに答えられれば十分です（演習 1 のローカルでの確認だけは、全員が行えます）。
>
> **コードは、ほとんど書きません。** 学生が行うのは、リポジトリの作成、Cloudflare と GitHub の設定、**1 行（版の番号）の書き換え**だけです。
>
> このモジュールだけ、**コース全体のリポジトリとは別の、新しいリポジトリ**を作ります（M5 で学んだ Secrets の登録を、**自分のアカウントの、本物のトークン**で、もう一度行います）。

## 1. 学ぶこと

- **デプロイ**とは何か。変更が、公開されるまでの**流れ**。
- **秘密の置き場**（GitHub の Secrets）と、**権限を最小限にする**意味。
- **自動デプロイ**の仕組み（ワークフローの読み方）と、**テストが通らなければ、公開されない**関門。
- **ロールバック**（前の版に戻す）の方法と、限界。
- 公開される**範囲**（誰が、何を見られるか）を、確かめる習慣。

## 2. デプロイとは

**デプロイ**とは、作ったコードを、**利用者が使える場所に、置く（公開する）**ことです。

```
  変更 → ブランチ → PR → CI（テスト） → レビュー → main にマージ → 自動デプロイ → 公開（URL）
  ──────── M1〜M4 で学んだ流れ ────────────────────────────────→  ← M10 で学ぶ部分
```

- 人が、手元から、直接公開すると、**テストも、レビューも、記録も、経由しません**。
- **自動化（CI）が公開する**と、**必ず、同じ手順**で行われ、**記録が残り**、**人は、公開用の鍵を持たなくて済みます**（M0・M5）。

## 3. 練習用の環境

| | 内容 |
|---|---|
| 公開先 | **Cloudflare Workers**（無料プラン）。`workers.dev` という、練習に使える公開用のアドレス（`https://<Worker の名前>.<あなたのサブドメイン>.workers.dev`）を使う |
| アプリ | `worker-template/` の、小さな Worker（あいさつを返すだけ） |
| 公開される範囲 | **URL を知っている人は、誰でも**見られる（インターネットに公開される） |

> **公開するものに、個人情報や、本物の秘密を、入れません。** この練習用の Worker は、データベースも、秘密も、個人情報も、使っていません。公開されるのは、コードが返す文面だけです。

実際のシステムでは、**練習用・staging・本番**の環境があります（M7）。ここで練習するのは、**自分専用の、練習用の環境**です。

## 4. 秘密の置き場と、トークンの権限

### 必要な秘密（2 つ）

| 名前 | 内容 | 置き場所 |
|---|---|---|
| `CLOUDFLARE_API_TOKEN` | **デプロイを行える、鍵**（API トークン） | GitHub の **Secrets**（自分のリポジトリ） |
| `CLOUDFLARE_ACCOUNT_ID` | デプロイ先の、アカウントの ID | GitHub の **Secrets** |

- M5 では、**偽の値**で、Secrets の登録を練習しました。今回は、**自分のアカウントの、本物のトークン**を登録します。
- **本物のトークンは、漏れると、他の人が、あなたのアカウントで、公開（デプロイ）できてしまいます。**

### トークンを作るとき（公式の資料の推奨）

- トークンの**テンプレート**の一覧から、**「Edit Cloudflare Workers」**を選ぶ（Worker を、編集できるだけの権限。Custom で組み立てる必要はない）。
- **最小限の範囲**に絞る（たとえば、**デプロイするアカウント 1 つだけ**）。
- 名前を付けて、何のためのトークンか、分かるようにする。

### 守ること

- トークンの値を、**コード、設定ファイル、チャット、AI、画面共有、スクリーンショットに、出さない**（M0）。
- 登録は、**一度きりの操作**。Secrets に登録したあとは、**値を、見られません**（M5）。
- **練習が終わったら、トークンを、削除（失効）します。**
- 漏れたかもしれないときは、**すぐに、そのトークンを失効して、新しく作り直し**、Secrets を更新します。

## 5. 自動デプロイの仕組み（ワークフローを読む）

`worker-template/.github/workflows/deploy.yml` の、流れです。

| ステップ | 内容 | 役割 |
|---|---|---|
| トリガー | `main` に変更が入ったとき | 公開の、きっかけ |
| `permissions: contents: read` | コードの読み取りだけ許す | 権限の最小化 |
| `npm ci` | 依存関係を、記録どおりに入れる | 同じ環境の再現 |
| `npm run check` | **型検査とテスト** | **通らなければ、ここで止まり、公開されない** |
| `cloudflare/wrangler-action` | Cloudflare に、公開する。**Secrets の 2 つを、ここで使う** | 公開 |

また、`ci.yml` は、**PR のときに**、型検査とテストを行います（**秘密は、使いません**）。

### 外部の「action」を使うことの意味

`cloudflare/wrangler-action@v4` は、**Cloudflare が公開している、他人（外部）が書いたコード**です。CI の中で、**あなたの Secrets を渡して、実行**します。

- 信頼できる提供元（今回は、Cloudflare の公式）のものを使う。
- 版の指定の仕方には、**タグ**（`@v4`。更新されると、中身が変わる）と、**コミットの固定**（変わらないが、更新が手間）がある。**どちらにも、長所と短所**がある（M4 の、依存パッケージの考え方と、同じ）。

## 6. ロールバック（前の版に戻す）

公開した版に、問題があったとき、**前の版に戻します**。

| 方法 | 内容 |
|---|---|
| **ダッシュボード** | Cloudflare の **Workers & Pages** → 自分の Worker → **Deployments** → 戻したい版の「…」→ **Rollback** |
| **コマンド** | `wrangler rollback`（版を選ぶか、版の ID を指定する）。自分のアカウントへのログインが必要 |
| **直して、再公開（基本）** | 問題の変更を、`git revert`（M1）で打ち消し、PR → CI → マージ → 自動デプロイ。**記録が残り、Git と本番が、ずれない** |

### 知っておくこと（公式の資料）

- ロールバックは、**指定した版を、新しいデプロイとして、100% の通信に反映**する。**すぐに**効く。
- 戻せるのは、**直近 100 版**まで。
- **Worker に結びついた資源（データなど）は、戻らない**。データの形が、版の間で変わっていると、古いコードが、エラーになることがある。
- **ロールバックは、緊急の応急処置**。戻すと、**Git の `main` と、公開されているものが、ずれる**。そのままにせず、**Git の側も直す**（直して、再公開）。
