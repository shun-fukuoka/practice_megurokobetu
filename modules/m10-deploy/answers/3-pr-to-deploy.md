# M10-3 の答えと解説

> 先に、自分の予想と観察を書き残してから読んでください。ローカルの部分（`npm run check`、`wrangler dev`）は、教材の作成時に確かめています。GitHub Actions での実行（PR の CI、マージ後の `Deploy`）と、Cloudflare への実際の公開は、2026-11-04 に、講師が実機で確かめました（結果は運営メモの確認記録）。

## 予想と結果

### ヒント

- `deploy.yml` の、**ステップの順序**を見る。
- ステップは、**上から順に**実行され、**失敗したら、その先は、実行されない**。

### 答え

| 問い | 答え |
|---|---|
| `main` にマージすると、自動で何が起きるか | `Deploy` ワークフローが動く。**依存関係の導入 → 型検査とテスト → Cloudflare への公開**の順 |
| テストが失敗する変更をマージしたら、公開されるか | **公開されない**。`npm run check` が失敗した時点で、ワークフローが止まり、**公開のステップに進まない** |
| 公開の確かめ方 | 公開された URL の `/health` を開き、`version` を見る |

### 手順 1（先に v1 を公開する）の補足

- 演習 1 の初回の `Deploy` は、Secrets が無く、`CLOUDFLARE_API_TOKEN` が無いというエラーで**失敗**する。**`Deploy` は `main` への push でだけ動く**ので、Secrets を登録しても、自動では、やり直されない。
- 何もしないと、**最初に成功する公開が `v2`** になり、Cloudflare の履歴に `v1` が無い。演習 4 の Rollback が、できなくなる。
- 失敗した実行を **Re-run all jobs** すると、**その実行の変更（コミット）の内容**で動くので、`v1` が公開される。**新しい変更を push しなくても、やり直せる**（演習 4 の、ずれを直す操作と、同じ）。

### 手順 8 の答え

- **関門のステップ**: `Type check and test`（`npm run check`）。公開のステップ（`Deploy Worker`）より**前**にあり、失敗すると止まる。
- **トークンは、誰の操作で使われたか**: **あなたの操作ではなく、ワークフロー（機械）**が、Secrets から取り出して使った。あなたは、**値を、手で入力していない**。
- **失敗する変更が `main` に入ったら**: PR の `ci.yml` を通らずに入った場合でも、`deploy.yml` の `npm run check` が**もう一度**止める。**公開は、前の正常な版のまま**。ただし、`main` の状態は壊れたままなので、**直す必要がある**。

## 振り返りの答え

- **通った関門**: 自分の確認（手元の `npm run check`）→ PR の CI（機械）→ マージ（人）→ デプロイ時の再検査（機械）。
- **利点**: **手元の環境の差**や**うっかり**に左右されない。**誰が・いつ・何を公開したか**が、履歴（Git と Actions）に残る。**トークンを、人が持ち歩かなくて済む**。

## 補足

- よくある失敗の原因: Secrets の名前の間違い（大文字小文字、アンダースコア）、トークンの権限・範囲、workers.dev のサブドメインが未登録。**ログの最初のエラー**を読む。
- 任意の手順 7 で CI が赤くなるのは、`test/greeting.test.ts` が、「こんにちは、はじめまして！」を期待しているため。
