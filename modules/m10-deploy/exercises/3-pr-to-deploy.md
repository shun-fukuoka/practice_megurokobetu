# 演習 M10-3: PR からデプロイまで

所要時間の目安: 35 分 / 対象: L1 / 前提: [演習 2](2-token-and-secrets.md)（Secrets を 2 件、登録済み）

## 目的

**1 行の変更が、PR → CI → マージ → 自動デプロイを通って、公開される**までを、体験する。テストが通らなければ、公開されないことも、確かめる。

> コードは書きません。**版の番号（`"v1"` → `"v2"`）を、1 行、書き換える**だけです。

## 手順

作業は、新しいリポジトリ（`hello-worker-practice`）のフォルダで行います。

### 0. 記録の Issue を作り、予想を書く（自分の力で）

[演習の進め方（M0 の 3b）](../../m0-orientation/README.md)に従い、「演習の記録」の Issue（演習: `M10-3`）を作ります。次の予想を、**実行する前に**書いてください。

1. 変更を `main` にマージすると、何が、自動で起きるか。
2. **テストが失敗する**変更をマージしたら、公開されるか。
3. 公開されたことを、どうやって確かめるか。

### 1. 先に、今の版（v1）を公開する

演習 1 で、新しいリポジトリを作った直後の `Deploy` は、Secrets が無くて**失敗**していました。そのため、**まだ、何も公開されていません**（`main` に変更が入るまで、`Deploy` は動きません）。このまま `v2` を公開すると、**公開の履歴に `v1` が無く**、演習 4 の「古い版へ戻す」ができません。

そこで、先に、**失敗していた `Deploy` を、Secrets を登録した今、もう一度動かします**。

1. GitHub の **Actions** タブで、**一番古い `Deploy`**（演習 1 の初回の、失敗した実行）を開く。
2. **Re-run all jobs** を押す（元の変更のまま、もう一度動く）。
3. すべてのステップが**緑**になることを確認する。
4. 次を開き、**`{"ok":true,"version":"v1"}`** と表示されることを確認する（`<サブドメイン>` は、演習 2 でメモしたもの）。

```text
https://hello-worker-practice.<サブドメイン>.workers.dev/health
```

> 再実行は、**その実行が使った変更（コミット）の内容**で動きます。そのため、`v1` のコードが公開されます。

### 2. ブランチを作る

```bash
git switch main
git pull
git switch -c practice/v2
```

### 3. 版を書き換える

エディタで、`src/greeting.ts` を開き、次の行を探します。

```ts
export const VERSION = "v1";
```

**`"v1"` を `"v2"` に書き換えて**保存します。

```bash
npm run check
```

型検査とテストが、通ることを確認します。

### 4. PR を出す

```bash
git add src/greeting.ts
git commit -m "practice: 版を v2 にする"
git push -u origin practice/v2
```

GitHub で、`main` 宛ての PR を出します。**PR の画面で、CI（`check`）が動き、緑になる**ことを確認します。

### 5. マージして、自動デプロイを見る

PR を、**マージ**します（自分のリポジトリなので、自分でマージします）。そのあと、GitHub の **Actions** タブで、**Deploy** ワークフローが動くのを確認します。実行のログを開き、各ステップ（`Install Dependencies`、`Type check and test`、`Deploy Worker`）が、**緑**になることを確認します。

> 失敗した場合は、ログの**最初のエラー**を読みます（よくある原因: Secrets の名前の間違い、トークンの権限・範囲、workers.dev のサブドメインが未登録）。分からないときは、**エラーの文を、秘密が入っていないことを確かめてから**、AI に、自分の言葉で状況を添えて質問します（M2）。

### 6. 公開されたかを確かめる

ブラウザで、次を開きます（`<サブドメイン>` は、演習 2 でメモしたもの）。

```text
https://hello-worker-practice.<サブドメイン>.workers.dev/health
```

`{"ok":true,"version":"v2"}` と表示されれば、**公開は、成功**です。トップページ（`/`）にも、「版: v2」と表示されます。

### 7. 【任意】テストが、公開を止めてくれる

1. 新しいブランチ（`practice/broken`）を作る。
2. `src/greeting.ts` の、`"こんにちは、はじめまして！"` の、**「は」を「わ」に**書き換える。
3. push して、PR を出す。**CI が、赤くなる**ことを確認する（テストが、失敗する）。
4. **マージは、しない**。PR を閉じ、ブランチは、そのままにして構わない。

### 8. 考える

- 手順 5 で、公開を行った**ワークフローの、どのステップ**が、「テストが通らなければ、公開されない」関門だったか。
- 公開に使われた**トークン**は、誰の操作で使われたか。あなたは、トークンの値を、**手で入力しましたか**。
- もし、`main` に、テストの失敗した変更が入ってしまったら、**公開は、どうなるか**（`deploy.yml` の順序を見る）。

### 9. 片づけの確認

`main` に切り替えて、最新を取り込みます。

```bash
git switch main
git pull
git status
```

`main` にいて、`working tree clean` であること（`VERSION` は、`v2`）。

## 振り返り

- 変更が公開されるまでに、**どの関門**（人・機械）を、通ったか。
- 人が、手元から公開する場合と比べて、この方法の利点は何か。
