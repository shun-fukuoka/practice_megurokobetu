# M10 確認の質問の答えと解説

> 先に、自分の言葉で答えを考えてから読んでください。答えは 1 つではありません。

## 1. デプロイとは何か。変更が公開されるまでの流れを、順に説明できるか。

**答えの例**: デプロイは、作ったアプリを、**インターネット上のサーバーに置いて、利用者が使える状態にする**こと。流れは、**ブランチで変更 → PR → CI（型検査とテスト）→ レビュー・マージ → `main` への変更をきっかけに、自動でデプロイ → 公開の確認**。

**押さえる点**: 「手元で動く」と「公開されている」は別。確認も、含める。

## 2. 人が手元から公開せず、自動化（CI）が公開する利点は何か。

**答えの例**: **人の環境の差やうっかり**に左右されない。**誰が・いつ・何を公開したか**が、履歴に残る。**テストを通ったものだけ**が公開される。**トークンを、人が持ち歩かなくて済む**。

**押さえる点**: 「再現できる」「記録が残る」「関門を通る」。

## 3. API トークンを、最小限の権限・範囲で作るのは、なぜか。漏れたかもしれないとき、何をするか。

**答えの例**: 漏れたときの被害を、**小さくする**ため（最小権限）。全部の権限だと、アカウント全体が、危険になる。漏れたかもしれないときは、**すぐに、そのトークンを失効（削除）し、新しく作り直して、Secrets を更新**する。

**押さえる点**: 「漏れない」ことに頼らず、「漏れても被害が小さい」設計にする。**失効が先**。

## 4. テストが通らないとき、公開されないのは、ワークフローのどの部分の働きか。

**答えの例**: `deploy.yml` の、**`npm run check` のステップ**が、公開のステップより**前**にあり、失敗すると、**以降のステップが実行されない**ため。

**押さえる点**: 「ステップは順に実行され、失敗したら止まる」。順序が、関門になる。

## 5. 外部の action を使うことには、どんなリスクがあるか。

**答えの例**: 外部の人が書いたコードを、**あなたの Secrets を渡して実行**する。提供元が乗っ取られたり、更新で悪意のある変更が入ると、**Secrets が盗まれうる**。対策は、**信頼できる提供元を選ぶ**こと、**版の指定（タグ／コミットの固定）の長所短所を理解**して選ぶこと、**権限を最小にする**こと。

**押さえる点**: タグは更新で中身が変わり、コミットの固定は変わらないが、更新が手間。

## 6. 公開した版に問題があったとき、どんな方法で戻せるか。ロールバックの限界は何か。ロールバックのあと、Git で何をするか。

**答えの例**: **ダッシュボードの Rollback**、**`wrangler rollback`**、**`git revert` して再公開**（基本）。限界は、**Worker に結びついた資源（データ）は戻らない**こと、**直近 100 版まで**であること、**Git の `main` とずれる**こと。ロールバックのあとは、**問題の変更を `git revert` で打ち消すか修正して、再度公開**し、Git と本番を一致させる。

**押さえる点**: ロールバックは**応急処置**。根本は、Git 側を直す。

## 7. 公開する前に、何を確かめるか。

**答えの例**: **公開される範囲**（誰が見られるか）、**返す内容に個人情報・秘密がないか**、**秘密がコードや設定にないか**、**トークンの権限と範囲**、**テストが公開の前に通る設定か**、**戻し方の準備**。

**押さえる点**: 一度公開すると取り消せないもの（個人情報の混入）を、最優先で確かめる。
