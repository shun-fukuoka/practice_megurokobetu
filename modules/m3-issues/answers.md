# M3 の答えと解説

> 先に、自分の考えを書き残してから読んでください。答えは1つではありません。ここに載せているのは「例」と「考え方」です。

## 設問1: 悪い Issue を直す

**依頼**: 「セッションの期限切れの判定、なんか分かりにくいから直しておいて」

### ヒント

1. 「分かりにくい」の主語は誰か（コードを読む人？画面を見る利用者？）。
2. 「直った」と言える状態を、何か**確認できる形**で言えるか。
3. 「ついでにやりたくなること」を、あらかじめ範囲の外に書いておけるか。

### 例

> **タイトル**: セッション無効の理由（`reason`）の種類が、呼び出し側から分かりにくい
>
> **背景**: `evaluateSession` が返す `reason` は、`"missing" | "idle" | "absolute"` の文字列で、画面に出すメッセージを作る側が、どの理由が何を意味するかをコードから読み取れない。
>
> **完了条件**
> - [ ] 各 `reason` の意味が、型の近くのコメントで説明されている
> - [ ] `reason` ごとの結果を確かめるテストが、すべて存在する
> - [ ] `npm run check` が通る
>
> **範囲**: 判定ロジック自体は変えない。画面のメッセージ作成は別の Issue。

### なぜ、この書き方か

- 依頼の「分かりにくい」は**曖昧**なので、誰が何に困っているかを**仮定として**書き、確認を取れる形にした。
- 完了条件は、「コメントがある」「テストがある」と**第三者が○×を付けられる**。
- 「画面のメッセージ作成」は、**ついでにやりたくなる**ことなので、範囲の外に明記した。

## 設問2: 自分の Issue

答えは1つではありません。次の観点で、自分の Issue を点検してください。

| 観点 | 良い状態 | よくある失敗 |
|---|---|---|
| 背景 | 誰が・何に困るかが分かる | 「〜したい」だけで理由がない |
| 完了条件 | 第三者が○×を付けられる | 「いい感じに」「適切に」 |
| 範囲 | 「やらないこと」が1つ以上ある | 書かない（→ レビューで範囲外の変更に気づけない） |
| 大きさ | PR 1本で終わる | 複数のことが混ざっている（→ 分ける） |

## 振り返りの答え

- 書いている途中で「決まっていない」と気づくのは、**良い兆候**です。決まっていないことを作業の前に見つけられた、ということだからです。
- 曖昧な言葉が入っていたら、「それは、どう確認するのか」と自問して、確認できる言葉に直します。
