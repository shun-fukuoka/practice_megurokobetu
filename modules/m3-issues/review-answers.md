# M3 確認の質問の答えと解説

> 先に、自分の言葉で答えを考えてから読んでください。答えは 1 つではありません。

## 1. 良い Issue の 4 つの要素を挙げ、それぞれが無いと、何が困るかを説明できるか。

**答えの例**

| 要素 | 無いと困ること |
|---|---|
| **背景**（誰が、何に困っているか） | 何のための変更か、後から分からなくなる。優先順位も付けられない |
| **完了条件**（第三者が○×を付けられる） | 「終わり」の基準がなく、レビューが「なんとなく」になる。作った人と頼んだ人で、終わりの認識がずれる |
| **範囲**（今回やらないこと） | 「ついでの変更」が紛れ込む。レビューで、範囲外の変更に気づけない |
| **大きさ**（PR 1 本で終わる） | 大きすぎて、レビューも、取り消しも、難しくなる。いつ終わるかも見えない |

**押さえる点**: 4 つの要素は、**あとから読む人（未来の自分を含む）が、迷わないため**のもの。

## 2. 「いい感じに直す」と書かれた完了条件を、どう書き直すか。

**答えの例**: 「いい感じ」を、**確認できる言葉**に置き換える。たとえば、「幅 375px の画面で、ボタン全体が画面内に収まる」「幅 1280px の見た目は変わらない」「`npm run check` が通る」のように、○×を付けられる形にする。

**押さえる点**
- 書き直す前に、**「何が困っているのか」を、依頼した人に確かめる**（分からないことは、分からないと言う）。
- 完了条件を書いている途中で「決まっていない」と気づいたら、それは、**作業の前に見つけられた良い兆候**。

## 3. Issue と Discussions は、どう使い分けるか。

**答えの例**: Issue は、**やることが決まっていて、完了条件が書けるもの**。Discussions は、質問、相談、方針の検討、「やるべきか」の議論など、**まだ作業になっていないこと**。迷ったら Discussions に書き、やることが決まったら Issue にする。

**押さえる点**: 議論の途中のものを Issue にすると、完了条件が書けず、いつまでも閉じない Issue が増える。

## 4. AI が自分の判断で Issue を作らないのは、なぜか。

**答えの例**: Issue は、チームの作業の単位で、**何をやるかを決める**ことだから。何を作業にするかは、人が判断する。AI には、起票案（題名・背景・完了条件）を出してもらい、人が読んで、起票するかを決める。

**押さえる点**
- AI は、不要な作業や、範囲の広すぎる作業を、たくさん作ってしまうことがある。
- 「提案は AI、決めるのは人」という、AI との役割分担の例（M2 の約束 7）。
