# M4 PR と CI

> 前提: [M1 Git とブランチの基本](../m1-git-basics/README.md)（ブランチ、add・commit・push の意味と操作）。この演習の `git switch -c`、`git add`、`git commit`、`git push` は、M1 で練習したものです。

所要時間の目安: 125 分（説明 25 分 ＋ 演習 105 分）

## 準備

自分のリポジトリで、題材のアプリを動かしてみます。

```bash
cd modules/m4-pr-and-ci/app
npm ci
npm run check
```

`npm run check` が緑（成功）になれば、準備は完了です。`check` は、CI（`.github/workflows/pr-check.yml`）が PR のたびに自動で行う確認と同じものです。

## 1. 変更が取り込まれるまでの流れ

```
main(正とする最新の状態)
   │
   ├─ ブランチを作る     ← 自分専用の作業場所。ここでは何を壊してもよい
   │     │
   │     ├─ 変更して、コミット
   │     └─ push して、PR(プルリクエスト)を出す
   │              │
   │              ├─ CI が自動で確認する（機械の確認）
   │              └─ 人がレビューする（人の確認）
   │
   └─ 問題なければ main にマージ
```

**main に直接変更を入れない**のが大原則です。必ず、PR を通します。

> このコースの自分のリポジトリでは、あなたがオーナーなので、main に直接 push しようと思えばできてしまいます。実際の開発では、権限と保護の設定で止められます（M5 で扱います）。ここでは、**自分で守る**習慣をつけます。

## 2. PR とは

「この変更を main に取り込んでください」という**提案**です。PR には、次を書きます。

- 何を変えたか、なぜ変えたか
- どうやって確認したか
- 不安な点

PR の目的は、**変更を人に説明し、他の人の目で確認してもらうこと**です。

## 3. CI とは

**CI(継続的インテグレーション)**は、PR が出されるたびに、**決まった確認を自動で、毎回同じように実行する仕組み**です。

人は、疲れます。急ぎのときは、確認を飛ばします。機械は、飛ばしません。

このリポジトリの CI が確認することは、次の2つのジョブです。

| ジョブ | 確認すること | 防げること |
|---|---|---|
| `verify` | コードの書き方の検査（lint）、型の検査、テストの実行 | 初歩的なバグ、書き間違い、壊れた変更 |
| `secret-scan` | PR の履歴に、秘密に見える文字列が無いか | 秘密の混入 |

### CI が緑なら安全か？ → いいえ

**CI が通る = 最低限の関門を越えただけ**です。次のことは、CI では分かりません。

- そもそも、頼まれた内容を実現しているか
- テストが書かれていない部分の動作
- 設計として正しいか、個人情報を適切に扱っているか

CI は「人のレビューの代わり」ではなく、**人が見る前の足切り**です。

### CI が赤いとき

1. PR の画面の「Checks」から、**赤いジョブを開く**
2. **最初にエラーが出た行**を探す（その後のエラーは、連鎖であることが多い）
3. エラーメッセージを読む。ファイル名と行番号が出ている
4. ローカルで `npm run check` を実行して、同じエラーを再現する
5. 直して、再度 push する（CI が自動で再実行される）

> 赤くなるのは、悪いことではありません。**問題を、早く、安く見つけてくれた**ということです。

## 4. レビュー

レビューで見るのは、動くかどうかだけではありません。

- Issue の「完了条件」を満たしているか
- 「範囲」の外を触っていないか
- 変更の意味が説明できるか（作者が、すべての行を説明できること）
- 秘密・個人情報が含まれていないか

AI が書いたコードでも、**PR の作者は人**です。「AI が書いたので分かりません」は、通りません。

## 5. PR が「競合」したとき（コンフリクト）

PR を出したあとに、**別の PR が先にマージされて `main` が進む**と、自分の PR が、**同じ場所を変更していて、自動では合わせられない**ことがあります。このとき、GitHub の PR の画面に、**「このブランチに競合がある」という趣旨の表示**が出ます（表記は、変わることがあります）。

| | 内容 |
|---|---|
| 原因 | 自分のブランチと `main` が、**同じ行を別々に変更**している（[M1 の 7 節](../m1-git-basics/README.md)と、同じ仕組み） |
| 起きても | **失敗ではなく、普通のこと**。PR の作者が、**自分で解消する** |
| 解消の流れ（手元） | ① `main` の最新を取り込む（`git fetch origin` → 自分のブランチで `git merge origin/main`）② 衝突したファイルを、**両方の内容を理解して**直す（M1-4 と同じ）③ `git add` → `git commit --no-edit` ④ **`npm run check` など、手元のテストをもう一度**行う ⑤ `git push` で PR を更新する。**CI が、もう一度動く** |
| GitHub の画面での解消 | 画面の「Resolve conflicts」から、ブラウザで直す方法もある。**小さな衝突なら使えるが、テストを動かせない**ので、手元をおすすめする |

- **解消したあとも、CI を通します。** 衝突の解消は、**人が内容を決めた変更**なので、自動で合わさったときより、**壊れやすい**のです。
- **片方の変更を、黙って捨てない。** 相手が書いた変更を消すときは、**PR の説明に書く**か、**相手に聞きます**。
- AI に解消を頼んだ場合は、**結果の差分（`git diff`）を、自分で読む**（M6）。

> この節の、GitHub の画面の表記と操作は、教材の作成時には、実際には確認していません。画面が違うときは、講師に伝えてください。
>
> **コンフリクトの解消は、この M4 が中心です**（手元での操作は [M1 の演習 4](../m1-git-basics/exercises/4-conflict.md)、PR の上での実際は[演習 4](exercises/4-pr-conflict.md)）。AI に解消を頼むときの注意は、[M6](../m6-ai-control/README.md) で、もう一度扱います。
