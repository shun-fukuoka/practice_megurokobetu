## 設問3: ローカルで出るエラー

### ヒント

1. 貼ったコードには、問題が**3種類**入っている。「書き方の規則」と「型の食い違い」が混ざっている。
2. lint は書き方の規則を見る。型の検査は、値の種類が合っているかを見る。
3. テストは、ここでは壊れていない（今回のコードはテストされていない）。

### 答え

| 確認 | 出るエラー | 該当箇所 |
|---|---|---|
| lint | `no-var`: `var` ではなく `let` か `const` を使う | 2行目 |
| lint | `eqeqeq`: `==` ではなく `===` を使う | 3行目 |
| 型 | `TS2367`: `number` と `string` の比較は常に偽で、意図しない比較に見える | 3行目 |

合計 **3件**です。`npm run check` は、lint → 型 → テストの順に実行し、**最初に失敗した時点で止まる**ため、手元では最初に lint の 2 件だけが見えます。lint を直すと、次に型のエラーが出ます。

## 設問5: ルールの理由

- **`no-var`**: `var` は、範囲（スコープ）の考え方が分かりにくく、意図しない再利用や上書きを起こしやすい。`let`/`const` は、範囲が明確。
- **`eqeqeq`**: `==` は、比べる前に型を自動で変換する。`0 == "0"` が真になるなど、予期しない一致が起きる。`===` は、型も一致して初めて真になる。
- **型の検査**: `count`（数値）と `"0"`（文字列）を比べても、型の上では絶対に一致しない。コードを書いた人の意図と、書かれた内容がずれているサイン。

## 振り返りの答え

- **最初に止まったのは lint**。実行順の最初で失敗し、そこで止まるため。
- **ローカルで先に実行する利点**: push 前に、数十秒で直せる。CI を待つ時間と、無料枠の実行時間を節約できる。
- **CI がなければ**: 動かして初めて気づく（または気づかずに本番に出る）。型のエラーは、特定の入力のときだけ誤動作する形で、後から見つかることが多い。
