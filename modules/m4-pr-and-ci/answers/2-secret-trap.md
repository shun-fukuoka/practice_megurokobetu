# M4-2 の答えと解説

> 先に、自分の予想と考えを書き残してから読んでください。

## 設問4: ログで見ること

### ヒント

- 検出結果には、ファイル名、行、コミットの識別子（ハッシュ）が出る。
- 値そのものが出ていないのは、ログから**二次的に漏れない**ようにするため。

### 答え

- `notes/leak-demo.txt` の、`github_token` の行が、最初にコミットしたコミットで検出される。
- `--redact` のため、値は伏せ字で表示される。CI のログは、リポジトリを読める人に見える場合があり、ログ自体が漏えい経路にならないようにする配慮。

## 設問5: 「消せば安全」か

### ヒント

- CI は「PR に含まれる**コミットの範囲**」を検査している。
- ファイルを消す変更は、**新しいコミットが1つ増える**だけ。

### 答え

**`secret-scan` は赤のままです。** 最初のコミットが PR に含まれ続けるためです。

ファイルを消しても、Git は**変更の履歴をすべて保存**しています。削除コミットの前の状態に、いつでも戻れます。つまり、秘密は履歴の中に残ります。

## 設問6: 本物の秘密をコミットしてしまったら

### ヒント

- 履歴から消す作業は、時間がかかる。その間に、何が起こりうるか。
- すでに、他の人や別のシステムがコピーしている可能性がある。

### 答え

**順番は、次のとおりです。**

1. **すぐに、その秘密を失効（無効化）して、再発行する。**
2. 管理者に報告する。
3. その後で、履歴の扱い（書き換え、再発行後の影響確認）を決める。

**失効が先の理由**: 履歴から消す作業の間にも、秘密が悪用されるかもしれないから。また、履歴から消しても、すでに複製・キャッシュされた可能性は消えない。**「漏れた可能性がある」時点で、その秘密はもう信用できない**ので、使えなくするのが最優先。

## 振り返りの答え

- **「入っていなかった」ことにできない理由**: Git は履歴を保存する仕組みであり、複製（クローン）も可能。一度 push された内容は、すべての複製から回収できない。
- **開発者に秘密を渡さない利点**: そもそも、開発者が漏らす経路が無くなる。誰かが退社しても、秘密を再発行する必要が（原則として）生じない。事故が起きた場合の影響範囲も、小さくなる。
