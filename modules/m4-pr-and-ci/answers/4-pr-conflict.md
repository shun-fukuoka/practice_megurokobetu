# M4-4 の答えと解説

> 先に、自分の予想と観察を書き残してから読んでください。手元の操作（`git merge origin/main` での衝突、解消、`git commit --no-edit`）は、教材の作成時に、ローカルのリモートで実際に確かめています。**GitHub の PR 画面の表示と、CI の再実行は、確かめていません。**

## 予想と結果

### ヒント

- 競合かどうかは、**合わせようとする時点の `main`** と、自分のブランチを比べて決まる。
- 出した時点で合わさっていても、**あとから `main` が進めば**、変わる。

### 答え

| 問い | 答え |
|---|---|
| 2 つの PR を出した直後 | **どちらも競合しない**（`main` は、まだ変わっていないので、それぞれ単独なら合わさる） |
| PR A をマージしたあとの PR B | **競合する**（`main` が進み、同じ行が別の内容になったため）。「競合がある」という趣旨の表示になり、そのままでは、マージできない |
| 解消して push したあとの CI | **動く**。push で PR が更新されるたびに、CI がもう一度動く |

### 手順 4 の印

```text
<<<<<<< HEAD
- 担当: 鈴木          ← 今いるブランチ（PR B）の内容
=======
- 担当: 田中          ← origin/main（PR A がマージされた後の main）の内容
>>>>>>> origin/main
```

### 手順 7 の答え

- **PR B の作者が解消する理由**: 衝突を起こしたのは、**あとからマージしようとする側の変更**で、その内容を一番分かっているのは作者だから。先にマージされた側は、すでに完了している。
- **解消のあとに、もう一度テストする理由**: 解消は、**人が内容を決めた変更**で、自動で合わさった変更より**壊れやすい**。2 つの変更が、**組み合わさって初めて壊れる**こともある。
- **相手の変更を黙って消したら**: 田中さんの変更が、**誰にも気づかれずに消える**。履歴には残るが、`main` の内容から消えるので、**気づくのが遅れる**。消すなら、**相手に聞く**か、**PR の説明に書く**。
- **AI に頼む場合**: 結果を `git diff` で読み、**両方の意図が残っているか**、**印が残っていないか**を確かめる。AI は、片方を黙って捨てることがある。

## 振り返りの答え

- **仕組み**: 2 つの PR が、**同じ行を別の内容に変更**していて、片方が先にマージされると、もう片方は、**自動では合わせられなくなる**。
- **最初にすること**: PR の画面で、**どのファイルが**競合しているかを見る。次に、手元で最新の `main` を取り込み（`git merge origin/main`）、**両方の内容を読む**。

## 補足

- 解消の方法には、**`main` を自分のブランチに取り込む（マージ）**やり方のほかに、**リベース**（自分の変更を、最新の `main` の先に付け替える）があります。リベースは、履歴が整う一方、**履歴を書き換える**ので、このコースでは扱いません。チームの方針に従ってください。
- GitHub の画面の「Resolve conflicts」は、**ブラウザで直せますが、テストを動かせません**。小さな衝突に限って使い、そのあと CI を確認します。
- 衝突を**減らす**には、**変更を小さく、早くマージする**こと、同じファイルを複数人が触るときは**事前に声をかける**ことが有効です。
