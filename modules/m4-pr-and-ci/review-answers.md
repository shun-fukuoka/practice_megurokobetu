# M4 確認の質問の答えと解説

> 先に、自分の言葉で答えを考えてから読んでください。答えは 1 つではありません。

## 1. なぜ main に直接 push しないのか。

**答えの例**: main は「正とする最新の状態」で、ほかの人も、これを土台に作業するから。直接 push すると、**誰の目も通らず、CI の確認も経ずに**、壊れた変更が入る。PR を通すことで、変更を人に説明し、CI とレビューの両方を通せる。

**押さえる点**
- 自分のリポジトリ（練習用）では、オーナーなので直接 push できてしまう。**実際の開発では、権限と保護の設定で止められる**が、ここでは自分で守る習慣をつける。
- PR は、**変更を人に説明し、他の人の目で確認してもらう**ための提案。

## 2. CI が緑でも、レビューが必要な理由を、1 つ挙げられるか。

**答えの例**（どれか 1 つで十分）
- CI は、**決まった機械的な確認**しかしない。「頼まれた内容を実現しているか」は、確認できない。
- テストが書かれていない部分は、壊れても気づけない。
- テストを弱められた（`skip`）場合、緑のまま問題が隠れる（M4-3 で見た例）。
- 設計として正しいか、個人情報を適切に扱っているかは、機械では分からない。

**押さえる点**: CI は、「人のレビューの代わり」ではなく、**人が見る前の足切り**。

## 3. CI が赤いとき、最初にどこを見るか。

**答えの例**: PR の画面の「Checks」から、**赤いジョブを開き、最初にエラーが出た行**を探す。ファイル名と行番号が出ているので、そのメッセージを読む。ローカルで `npm run check` を実行して、同じエラーを再現してから直す。

**押さえる点**
- 「最初の」エラーを見る理由: その後のエラーは、連鎖であることが多い。
- 赤くなるのは悪いことではなく、**問題を早く、安く見つけてくれた**ということ。
- 読んでも分からないエラーは、**そのメッセージを AI に貼り、自分の言葉で状況を添えて質問する**（秘密が入っていないか、貼る前に確認する）。

## 4. 秘密を、そもそも開発者に渡さない仕組みにする利点は何か。

**答えの例**: 開発者が漏らす経路が、そもそも無くなる。開発者が退社しても、秘密を再発行する必要が（原則として）生じない。事故が起きたときの影響範囲も、CI と管理者に限られる。

**押さえる点**: 秘密は「うっかり」で漏れる。**うっかりが起きない設計**にするのが、仕組みで守る、ということ。

## 5. AI が書いた差分を、レビューするときに、まず何を見るか。

**答えの例**: **変更されたファイルの一覧**を見て、Issue の範囲と合っているかを確かめる。次に、テストの変更（`skip` の追加、期待値の書き換え）と、依存の追加を、特に注意して読む。本体のコードの変更は、**判断できないときの振る舞い**（閉じる側に倒れているか）を見る。

**押さえる点**: 「テストが通っている」ことは、安全の証明にならない。範囲外の変更や、テストの弱め方に気づくのが、人のレビューの役割。

## 6. PR が競合したとき、誰が、どう解消するか。解消したあと、何をもう一度行うか。

**答えの例**: **PR の作者が**、自分で解消する。`main` の最新を自分のブランチに取り込み、衝突したファイルを、**両方の内容を理解して**直し、`git add` と `git commit` で記録して、`git push` で PR を更新する。**解消したあとは、手元のテストと CI を、もう一度通す**。

**押さえる点**
- 衝突の解消は、**人が内容を決めた変更**なので、自動で合わさったときより、壊れやすい。
- 相手の変更を黙って捨てない（聞く、または PR に書く）。
- AI に頼んだ場合も、結果の差分を自分で読む。
