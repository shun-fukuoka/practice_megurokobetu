# M5 確認の質問の答えと解説

> 先に、自分の言葉で答えを考えてから読んでください。答えは 1 つではありません。

## 1. Secrets に登録した値を、あとから見られるか。見られないことの利点は。

**答えの例**: 見られない。更新（上書き）はできるが、登録した値を画面から読み出すことはできない。利点は、**登録した本人や管理者でも、うっかり漏らせない**こと。画面の共有やスクリーンショット、権限のない人の閲覧から、値が漏れにくくなる。値は、ワークフローの中でだけ使える。

**押さえる点**
- ログでは `***` に置き換わる（マスク）が、**万能ではない**。値を加工して出力すると、隠れない。**秘密をログに出さない**のが本当の対策。
- Variables は、秘密でない設定値で、あとから見られる。違いは、「見える設定」か「見えない設定」か。

## 2. コラボレーターに、なぜ「最小の権限」だけを渡すのか。

**答えの例**: 必要以上の権限は、**間違い、うっかり、悪用**のときの被害を大きくするから。Write で足りる人に Admin を渡すと、設定や Secrets の変更、リポジトリの削除までできてしまう。必要な作業ができる、最小の権限だけを渡す。

**押さえる点**
- Read ／ Write ／ Admin のできること（M5 の表）を、自分の言葉で説明できる。
- **権限は、外すところまでが仕事。** 抜けたメンバーの権限を外し忘れるのは、使われない鍵を放置するのと同じ。

## 3. 実際の開発で、あなたが Secrets に触れない理由は。

**答えの例**: 実際の開発では、あなたは**メンバー（Write）**で、**オーナー（Admin）ではない**から。設定と Secrets は、管理者と CI だけが持つ設計にしている。開発者に秘密を渡さないことで、漏えいの経路を減らし、退社時の再発行も不要にできる。

**押さえる点**
- 練習のリポジトリでは自分がオーナーなので触れるが、**実際の開発とは立場が違う**。
- 触れなくても開発できる仕組み（ローカルの環境、CI が秘密を持つ）になっている（M7）。
