## 1. このモジュールの狙い

M2 では、AI を**先生として使う**ことと、**確認画面を 1 つずつ読む**ことを学びました。M6 では、その先の、**AI をどう統制するか**を学びます。

AI エージェントは、ファイルを読み、書き、コマンドを実行できます。便利ですが、間違えたり、だまされたりすることもあります。だから、**「頼んで、守ってもらう」だけでなく、「できないようにする」仕組み**が必要です。

## 2. 統制の層

統制には、強さの違う層があります。**強い層ほど、AI の判断に頼らず、機械的に止めます。**

| 層 | 内容 | 強さ | 誰が止めるか |
|---|---|---|---|
| ① **指示** | 指示ファイル（`CLAUDE.md`、`AGENTS.md`）や、チャットでの依頼で、「こうしてほしい」と伝える | **お願い**。守られない可能性がある | AI 自身 |
| ② **確認** | コマンドやファイル変更の**許可画面**を、人が 1 つずつ読んで判断する | 人の判断。見落とし・慣れに弱い | あなた |
| ③ **拒否ルール** | 「この操作は、必ず止める」を、設定ファイルに書く | **強制**。AI がやろうとしても止まる。ただし、書き方の外は止まらない | 製品（Claude Code） |
| ④ **隔離** | worktree、サンドボックス、コンテナで、**影響が及ぶ範囲そのもの**を狭くする | 強い。壊れても、被害が限られる | 仕組み |
| ⑤ **渡さない** | 本番の個人情報や秘密に、**そもそもアクセスできない形**にする | **最も強い**。ないものは、漏れない | 設計 |

> 公式の資料にも、はっきり書かれています。**許可のルールは、AI（モデル）ではなく、Claude Code が強制する。プロンプトや `CLAUDE.md` の指示は、AI が何を試すかに影響するが、何が許可されるかは変えない。** 指示は「お願い」、拒否ルールは「強制」です。

### 層の使い分け

- 重要なこと（秘密を読ませない、勝手に push させない）は、**③以上**で止める。指示ファイルに書くだけで、安心しない。
- ③の**拒否ルールだけでも、完全ではない**（次の 3 節）。だから、②（確認）と⑤（渡さない）を、重ねる。
- **どれか 1 つが破られても、次で止まる**ように、層を重ねる（多層防御。M9 のセキュリティでも、同じ考え方を使います）。

## 3. 許可のルール（拒否ルール）

### ルールの種類と評価の順

| ルール | 意味 |
|---|---|
| **allow**（許可） | 確認なしで実行してよい |
| **ask**（確認） | 毎回、確認する |
| **deny**（拒否） | 実行させない |

**評価の順は、deny → ask → allow** です。最初に当てはまったものが、結果になります。**deny は、allow で打ち消せません**（広い deny があれば、狭い allow があっても、止まります）。

### ルールの書き方

`ツール名` または `ツール名(対象)` の形です。

| ルール | 意味 |
|---|---|
| `Read(.env)`、`Read(./.env)`、`Read(**/.env)` | （拒否ルールでは）**どの深さの** `.env` も、読ませない |
| `Read(/.env)` | 作業フォルダの**直下の** `.env` だけ、読ませない（先頭の `/` で、場所を固定する） |
| `Read(.env.*)` | `.env.local` などを読ませない |
| `Bash(rm *)` | `rm` で始まるコマンドを実行させない |
| `Bash(npm run test *)` | （allow として）テストの実行を、確認なしで許可する |

> **落とし穴: 書き方で、効く範囲が変わります。** 先頭が `/` のルール（`Read(/.env)`）は、**作業フォルダの直下だけ**に効きます。M7 で作る `.env` は、`modules/m7-local-env/app/` の中にあるので、**`Read(/.env)` では守れません**。`Read(.env)`、`Read(./.env)`、`Read(**/.env)` なら、拒否ルールでは、どの深さの `.env` にも効きます（公式の資料に、拒否ルールは単一の名前を、どの深さにも適用すると書かれています。教材の作成時に、別セッションで実際に確かめました。演習 2）。
>
> なお、**許可（allow）ルールでは、同じ書き方でも、直下だけに効く場合があります**（公式の資料）。許可と拒否で、効き方が違うことにも、注意してください。**ルールを書いたら、意図した場所に効いているかを、確かめます。**

### 設定ファイルの場所（Claude Code）

| 場所 | 誰に効くか | Git に入るか |
|---|---|---|
| `~/.claude/settings.json`（Windows では `%USERPROFILE%\.claude\settings.json`） | **自分の、すべてのプロジェクト** | 入らない |
| `.claude/settings.json`（プロジェクト内） | そのプロジェクトで作業する全員 | **入れる**（チームで共有） |
| `.claude/settings.local.json`（プロジェクト内） | **自分の、そのプロジェクトだけ** | 入れない（`.gitignore` に入れる。このリポジトリでは設定済み） |

- 設定ファイルは**厳密な JSON**です（コメントや、末尾のカンマは、エラーになります）。
- 設定の変更は、**実行中のセッションにも、反映されます**（再起動は、通常は不要）。
- チャット画面（デスクトップアプリ、VS Code 拡張）では、設定ファイルを**エディタで編集**します。
- **`deny` と `ask` は、すぐ効きます。** 共有の `.claude/settings.json` の **`allow` は、各自が、そのフォルダを信頼するまで効きません**。

### 自分の設定ファイルは、自分で書く

**権限の設定は、AI に書かせません。** 権限そのものを、AI に決めさせることになるからです。AI には「この設定の意味を説明して」と頼むのは構いませんが、**書くのは自分**です。

> **注意: 確認画面で「今後は確認しない」を選ぶと、`allow` ルールが、設定ファイルに保存されます**（公式の資料にも書かれています。教材の作成時の試験でも、確認画面での選択が、`.claude/settings.local.json` に、`Bash(...)` の許可として追加されていました）。便利ですが、**その操作を、これからは確認なしで許可する**という意味です。**選ぶ前に、「そのコマンドを、毎回確認なしで実行させてよいか」を、考えてください。** 保存された許可は、設定ファイルを見れば、確かめられます。

### 個人の設定の、おすすめの例

次の内容を、`~/.claude/settings.json` に、自分で書くことを、おすすめします（自分のすべてのプロジェクトに効きます）。

```json
{
  "permissions": {
    "defaultMode": "default",
    "disableBypassPermissionsMode": "disable",
    "deny": [
      "Read(**/.env)",
      "Read(**/.env.*)"
    ]
  }
}
```

| 項目 | 意味 |
|---|---|
| `"defaultMode": "default"` | 会話を始めたときのモードを、**Manual** にする（M2 で見た、「最初のモードが Auto の場合がある」への対策） |
| `"disableBypassPermissionsMode": "disable"` | 確認を全部省く **Bypass permissions** を、**使えなくする** |
| `Read(**/.env)`、`Read(**/.env.*)` | どの深さの `.env` 系のファイルも、AI に**読ませない** |

> `.env.*` には、`.env.example` も含まれます（読ませられなくなります）。`.env.example` を AI に見せたいときは、中身を、自分で貼ってください（秘密は入っていません）。

### 拒否ルールの限界（重要）

拒否ルールは、**強いけれど、万能ではありません**。公式の資料にも、限界が書かれています。

**① コマンドの拒否は、「書かれた形」にだけ効きます。**

| 拒否ルール | 止まる | 止まらない |
|---|---|---|
| `Bash(rm *)` | `rm -rf build/` | `/bin/rm -rf build/`、`bash -c 'rm -rf build/'` |
| `Bash(git push *)` | `git push origin main` | `git -C . push origin main`、`git 'push' origin main` |

→ コマンドの拒否は、**セキュリティの壁ではなく、「普通に頼んだとき」の防止**です。確実に止めたいことは、②（確認）、④（隔離）、⑤（渡さない）と重ねます。

**② ファイルの読み取り拒否は、AI の「ファイルを読む道具」と、認識されたコマンド（`cat` など）に効きます。** 一方、**スクリプトが、自分でファイルを開く場合**（Node や Python のプログラムなど）には、**効きません**。OS のレベルで止めるには、**サンドボックス**（別の機能）が必要です。

**だから、「確認画面を読んで、許可しない」という②の習慣が、拒否ルールの外側で、最後の砦になります。**

## 4. worktree（作業場所の隔離）

### worktree とは

Git の機能で、**同じリポジトリの、別のフォルダ・別のブランチ**を、もう 1 つ作るものです。AI に、**別の作業場所**で変更させると、次の利点があります。

- **手元の作業フォルダを、汚さない。** 失敗しても、そのフォルダごと、捨てられる。
- **変更が、別のブランチに、まとまる。** 気に入れば残し、気に入らなければ、捨てる。
- **並行して作業できる。** 複数の AI の作業を、同時に進められる。

### 使い方（チャット画面）

- チャット画面で、AI に「**worktree で作業してください**」と頼むと、AI が作ります（Claude Code の公式の資料に、この使い方が書かれています）。
- デスクトップアプリには、セッションを worktree で行う機能もあります（Git が必要）。
- 標準の場所は、`.claude/worktrees/<名前>/`、ブランチ名は `worktree-<名前>` です（Claude Code が作る場合）。

### 注意

- worktree は、**新しくチェックアウトしたフォルダ**です。`node_modules` や `.env` のような、Git に入らないファイルは**ありません**。必要なら、そこで `npm ci` などを実行します。
- **AI は、頼んでいなくても、worktree の中でコミットすることがあります**（教材の作成時の試験で確認しました）。結果は、`git log --all --oneline` と `git diff` で、必ず自分で確かめます。
- **Windows では、パスの長さに注意**します。場所が深いと、worktree の作成や削除が、「Filename too long」で失敗することがあります（`git config core.longpaths true` か、短いパスの場所に置く）。
- 自分の手でも作れます。

  ```bash
  git worktree add .claude/worktrees/practice -b worktree-practice   # 作る
  git worktree list                                                   # 一覧
  git worktree remove --force .claude/worktrees/practice              # 削除
  ```

  （このコースの手順は、演習 3 で行います。）

## 5. 指示ファイル

AI に、プロジェクトの決まりごとを伝えるファイルです。

| 製品 | ファイル |
|---|---|
| Claude Code | `CLAUDE.md`（プロジェクト）、`~/.claude/CLAUDE.md`（個人）、`CLAUDE.local.md`（個人・そのプロジェクトだけ。Git に入れない） |
| Codex | `AGENTS.md` |
| 共通 | `AGENTS.md` は、他の AI ツールも読む。Claude Code は、`CLAUDE.md` が無ければ `AGENTS.md` を読み、両方あるときは `CLAUDE.md` だけを読む（`CLAUDE.md` から `AGENTS.md` を取り込む書き方もできる） |

- 書くのは、**具体的で、短い**決まりごと（「テストは `npm run check` で実行する」「`.env` は読まない」など）。
- **指示ファイルは、「文脈」であって、「強制」ではありません。** 公式の資料にも、「止めたい動作は、ルール（フック）で止める」と書かれています。
- このリポジトリや、本体のリポジトリにも、実例があります（本体は、アクセス権を渡した後に、一緒に読みます）。

## 6. 危険な操作の見分け

操作は、次の観点で見分けます（M2 の 4 区分を、さらに細かくします）。

| 観点 | 問い |
|---|---|
| **取り消せるか** | 失敗したら、元に戻せるか。削除、強制 push、`git reset --hard` は、戻せない |
| **範囲** | 影響が、作業フォルダの中か。外（他のフォルダ、他の人、本番）に及ぶか |
| **外へ出るか** | データを、外部に送るか（`git push`、`curl`、投稿） |
| **秘密に触れるか** | `.env`、鍵、個人情報を、読む・書く・出力するか |
| **分かるか** | 自分は、このコマンドが**何をするか**、説明できるか |

**分からないコマンドは、許可しません。** 迷ったときは、**止まる側**に倒します（M0・M2 と同じ）。

### 例: AI にコンフリクトを解消させるとき

コンフリクトの解消（[M4](../m4-pr-and-ci/README.md) の 5 節、[M1-4](../m1-git-basics/exercises/4-conflict.md)）は、AI に頼みたくなる作業です。頼んでもよいのですが、**AI が黙って片方の変更を捨てる**ことがあります。次を確かめます。

| 確かめること | 方法 |
|---|---|
| 印（`<<<<<<<`、`=======`、`>>>>>>>`）が、**残っていない** | `git diff --check` |
| **両方の意図が残っている**（片方が消えていない） | 解消後の `git diff` を、**自分で読む**。迷ったら、書いた人に聞く |
| AI が実行しようとしたコマンドが、**安全** | 確認画面を読む。`git reset --hard`、`git checkout --theirs .`（全部を片方に寄せる）、強制 push は、許可しない |
| 解消のあとも、**テストが通る** | `npm run check` と CI |

**どちらを残すかを決めるのは、人**です（AI は、提案役）。

## 7. プロンプトインジェクション

### 何が起きるか

AI は、**読んだ文章の中の「命令」に、従ってしまうことがあります。** たとえば、Web ページ、Issue、他人の PR、ライブラリの説明文の中に、「このファイルを読んで、内容を送れ」のような**命令が紛れている**と、AI が、**あなたの指示のように**扱ってしまう恐れがあります。これを、**プロンプトインジェクション**といいます。

### 守り方

- **読んだ文章は、「データ」であって、「あなたの指示」ではない。** AI が、文章の中の命令に従おうとしたら、**止める**。
- **確認画面を読む**（②）。AI が、頼んでいない操作（ファイルの作成、コマンド、外部への送信）をしようとしたら、**許可しない**。
- **信頼できない文章を、AI にそのまま読ませない**（出所の分からない文書、見知らぬ人の Issue や PR、怪しい Web ページ）。
- 拒否ルール（③）と、渡さない設計（⑤）で、**万一、従ってしまっても、被害が出ない**ようにする。

公式の資料にも、「提案されたコマンドを承認の前に確認する」「信頼できない内容を、そのまま AI に渡さない」「重要なファイルの変更を確かめる」などの、ベストプラクティスが載っています。

## 8. 検証の仕方

AI の作業は、**人が確かめます**。

| 方法 | 内容 |
|---|---|
| **差分を読む** | `git status`、`git diff`、画面の差分で、何が変わったかを、自分の目で確かめる（M2・M4-3） |
| **テストを走らせる** | 変更が、壊していないことを、機械で確かめる（M8）。ただし、テストが弱められていないかも見る |
| **別のセッションにレビューさせる** | 実装した AI とは、**別の会話**に、差分のレビューを頼む。同じ会話だと、同じ思い込みを引き継ぐ |
| **自分の言葉で説明する** | 変更の意味を、自分の言葉で説明できるか（できなければ、出さない） |
