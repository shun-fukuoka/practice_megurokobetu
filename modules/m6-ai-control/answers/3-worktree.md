# M6-3 の答えと解説

> 先に、自分の予想と観察を書き残してから読んでください。この演習は、教材の作成時に、**別セッションで実際に試しました**（Claude Code のデスクトップアプリ。2026-10-30。**1 回の観察**）。あなたの環境（バージョン、パスの長さ、使い方）で、同じとは限りません。違う場合は、講師に伝えてください。

## 予想と結果

### ヒント

- worktree は、**別のフォルダ・別のブランチ**。元のフォルダとは、ファイルが別。
- 変更は、worktree の中のファイルに入る。

### 答え

| 確認 | 結果 |
|---|---|
| **元のフォルダ**の `git status` | **変更は表示されない**（変更が、別のフォルダに隔離されているため） |
| `git worktree list` | **行が 1 つ増える**。標準では、`.claude/worktrees/<名前>/` の下に作られ、ブランチ名は `worktree-<名前>` になる（Claude Code が作る場合。デスクトップアプリで作る場合は、場所や名前が異なることがあるので、**表示された内容を、そのまま確認する**） |
| **worktree の中**の `git status`、`git diff` | 頼んだ変更（1 ファイル、1 行）が表示される |

元のフォルダが汚れないので、**失敗しても、そのまま捨てられます**。

## 実際の観察（模擬実行）

「worktree で作業してください。…コメントに、説明を 1 行だけ足してください。ほかのファイルは、変更しないでください。」と頼んだ結果です。

| 確認 | 結果 |
|---|---|
| 元のフォルダの `git status` | **空**（変更は入らなかった。`session-policy.ts` も、元のまま）。隔離は、成功した |
| worktree の場所と名前 | `.claude/worktrees/session-policy-comment/`、ブランチは `worktree-session-policy-comment`（**名前は、AI が決めた**） |
| 変更の内容 | 1 ファイル、1 行の追加（頼んだとおり）。範囲外のファイルは、変わっていなかった |
| **頼んでいない操作** | **AI が、自分でコミットした**（`git log` に、1 コミットが増えた）。push と PR は、していなかった |
| 作成の途中 | **最初は、失敗した**（Windows のパスが長すぎて、一部のファイルを書き出せなかった）。AI は、`core.longpaths` を一時的に有効にして、手動で worktree を作り直した。そのため、worktree の `git status` には、書き出せなかったファイルが、変更扱いで表示された（コミットには、含まれていなかった） |
| 確認画面 | worktree を作るなどのコマンドで、**許可の確認が出た**（あなたが読んで許可する） |

### この観察から分かること

- **隔離は、効いた。** 元のフォルダは、汚れなかった。
- **AI は、頼んでいないコミットをした。** 「1 行だけ足して」と頼んでも、コミットまで進めることがある。**だから、worktree の結果を、必ず自分で確かめる**（`git log --all --oneline`、`git diff`）。コミットを、取り消す・残すは、自分が決める。
- **Windows では、パスの長さが問題になる。** この試験の場所（深いフォルダ）では、作成も削除も、「Filename too long」で、うまくいかなかった。短いパスの場所に置く、または `git config core.longpaths true` を設定する。
- **片づけでは、`git branch -d` が拒否される**（コミットがあるため）。中身を確かめて、練習のものだと分かってから、`git branch -D` を使う。

## 片づけの流れ

```bash
git worktree remove --force <場所>    # worktree のフォルダを消す
git branch -d <ブランチ名>             # 作られたブランチを消す
```

- `git worktree remove` は、変更があるときは `--force` が必要。
- `git branch -d` は、**マージ済み**のブランチだけ消せる。AI が worktree の中でコミットしていると、「まだマージされていない」と拒否される。**中身を確かめて、練習のものだと分かってから**、`-D`（強制）を使う。強制削除は、取り消せない。

## 手順 6: 考える

- **worktree の利点**: 手元の作業フォルダを、汚さない。変更が、別のブランチにまとまり、気に入らなければ、**まるごと捨てられる**。並行して、複数の作業を進められる。手元で直接作業させる場合は、AI の変更が、今の作業と混ざり、**どれが AI の変更か、分からなく**なる。
- **`node_modules` や `.env` が無い問題**: worktree は、新しくチェックアウトしたフォルダなので、Git に入らないファイルが、ありません。AI に、worktree の中でテストを実行させるには、**そこで `npm ci` などで、依存関係を入れる**必要がある。`.env` のように、Git に入らないファイルを、自動でコピーする仕組み（`.worktreeinclude`）もあるが、**`.env` をコピーするかは、慎重に判断**する（M0・M2 の、秘密を渡さない方針）。
- **差分が、範囲を超えていたら**: その変更は、**取り消す**（または、worktree ごと捨てる）。範囲を、もう一度伝えて、やり直してもらう。範囲外の変更を、そのまま取り込まない（M4-3 と同じ）。

## 振り返りの答え

- **「捨てられる」ことが、安心につながる理由**: 失敗の被害が、**その worktree の中**に限られる。気に入らなければ、削除するだけで、元に戻る。**「やり直せる」と分かっていると、AI に、思い切って任せられる**。
- **残す場合の流れ**: worktree のブランチで、変更を確認し（差分を読む）、コミットする → push して、PR を作る（M4） → CI が走り、レビューを受ける → マージ。**AI が作った変更も、人が作った変更と同じ関門を通す**。
