# 演習 M6-3: worktree で作業して、捨てる

所要時間の目安: 25 分 / 前提: [README](../README.md) の 4 節、[演習 2](2-instruction-vs-deny.md)（片づけの確認まで終えていること）

## 目的

- AI の作業を、**別の作業場所（worktree）に隔離**する。
- 手元の作業フォルダが、**汚れない**ことを確かめる。
- 作業の結果を確認して、**捨てる**（必要なら、残す判断もできる）。

> モードは、**Manual** にしてください（会話を始める前に、画面のモード表示を、自分の目で確かめます）。
>
> **Windows の注意**: リポジトリの場所のパスが長いと、worktree の作成や削除が、「Filename too long」で失敗することがあります。事前に、そのリポジトリだけ、`git config core.longpaths true` を実行するか、リポジトリを、パスの短い場所（例: `C:\work\`）に置きます。
>
> **AI は、頼んでいなくても、コミットすることがあります。** 手順 3 で、確かめます。

## 手順

### 0. 記録の Issue を作り、予想を書く（AI を使わずに）

[演習の進め方（M0 の 3b）](../../m0-orientation/README.md)に従い、「演習の記録」の Issue（演習: `M6-3`）を作ります。次の予想を、**AI を使う前に、自分の力で**書いてください。

- AI が worktree で作業したとき、**手元のフォルダ**（今開いているフォルダ）で `git status` を実行すると、変更は表示されるか。
- worktree は、どこに作られ、どんなブランチになると思うか。

### 1. 始める前の状態を確かめる

自分のターミナルで、次を実行します。

```bash
git status
git worktree list
```

`git status` に変更が出ないこと、`git worktree list` が **1 行だけ**（今のフォルダ）であることを確認します。**これが、片づけで戻す状態です。**

### 2. worktree での作業を頼む

チャット欄に、次のように入力します。

> 「worktree で作業してください。`modules/m4-pr-and-ci/app/src/session-policy.ts` の、いちばん上のコメントに、説明を 1 行だけ足してください。ほかのファイルは、変更しないでください。」

AI が、許可の確認画面を出したら、**内容を読んで**から、許可します（worktree を作るコマンドなどが出ます。分からないものは、許可せず、チャットで「これは、何をするのですか」と聞きます）。

### 3. 変更が、どこに入ったかを確かめる

自分のターミナルで、**元のフォルダ**（今開いているフォルダ）から、次を実行します。

```bash
git status
git worktree list
```

次を、記録の Issue のコメントに書きます。

- `git status` に、変更は表示されたか（**予想と、合っていましたか**）
- `git worktree list` に、増えた行は何か（**場所と、ブランチ名**）
- AI は、**頼んでいない操作**（コミット、push など）をしていないか。`git log --all --oneline` で、頼んでいないコミットが、増えていないかを確かめる。

次に、増えた worktree の場所に移動して、確認します（`<場所>` は、`git worktree list` に表示された、増えた行のパスです）。

```bash
cd <場所>
git status
git diff
```

AI が、頼んだとおりの変更（1 ファイル、1 行）をしているかを、**差分を読んで**確かめます。

### 4. 判断する

- 差分は、頼んだ範囲に収まっているか（範囲外のファイルが、変わっていないか）。
- **この演習では、捨てます**（気に入った場合は、本来は、このブランチをコミットして、PR にします）。

### 5. 片づける

元のフォルダに戻り（`cd` で、元のフォルダに戻ります）、次を実行します（`<場所>` と `<ブランチ名>` は、手順 3 で確認したものです）。

```bash
git worktree remove --force <場所>
git branch -d <ブランチ名>
```

> `git worktree remove` が「Filename too long」で失敗した場合は、Windows のパスの長さが原因です。worktree の登録は消えても、**フォルダが一部残る**ことがあります。`git config core.longpaths true` を設定して、もう一度試すか、残ったフォルダを、エクスプローラーなどで削除します。
>
> `git branch -d` が「まだマージされていない」と拒否した場合は、worktree の中に、AI が**コミット**を作ったということです（AI は、頼んでいなくても、コミットすることがあります）。**中身を確認し、練習のものだと確かめてから**、`git branch -D <ブランチ名>`（強制削除）を使います。強制削除は、取り消せません。

チャットの会話も、閉じます（または、新しい会話に切り替えます）。

**片づけの確認**: 元のフォルダで、次を実行します。

```bash
git status
git worktree list
git branch
```

`git status` に何も表示されない、`git worktree list` が 1 行だけ、`git branch` に `worktree-` で始まるブランチが無いこと。

### 6. 考える

- worktree で作業させる利点は、何か。手元のフォルダで、直接作業させる場合と、何が違うか。
- worktree は「新しくチェックアウトしたフォルダ」なので、`node_modules` や `.env` がありません。AI に、worktree の中で**テストを実行**させたい場合、何が必要か。
- 差分が、頼んだ範囲を超えていたら、どうするか。

## 振り返り

- 「捨てられる」ことは、AI に任せるときの、安心につながる。それは、なぜか。
- worktree で作業した結果を、**残す**場合の流れを、説明できるか（ブランチ → PR → CI → レビュー）。

答えは [answers/3-worktree.md](../answers/3-worktree.md)。見たあと、記録の Issue に「答えを見て気づいたこと」をコメントし、Issue を閉じます。
