# M6 確認の質問の答えと解説

> 先に、自分の言葉で答えを考えてから読んでください。答えは 1 つではありません。

## 1. 統制の 5 つの層を挙げ、「指示」と「拒否ルール」の違いを説明できるか。

**答えの例**: 強さの違う 5 つの層がある。①**指示**（指示ファイル、チャットでの依頼）、②**確認**（許可画面を、人が読む）、③**拒否ルール**（設定ファイルで、操作を止める）、④**隔離**（worktree、サンドボックス、コンテナ）、⑤**渡さない**（秘密や個人情報に、そもそもアクセスできない形にする）。指示は、AI への「お願い」で、守られるかは AI 次第。拒否ルールは、製品が**強制**し、AI がやろうとしても止まる。

**押さえる点**
- 強い層ほど、**AI の判断に頼らない**。
- どれか 1 つが破られても、次で止まるように、**重ねる**（多層防御）。

## 2. 指示ファイルに「`.env` を読まない」と書くだけで、安心できないのは、なぜか。

**答えの例**: 指示ファイルは「文脈」であって、**強制ではない**から。AI が、ユーザーの強い依頼や、ほかの文脈とぶつかったとき、守らないことがある。しかも、ファイルを**読む**操作は、確認画面なしで行われるので、気づかないうちに読まれうる。止めたいなら、**拒否ルール以上**で止める。

**押さえる点**: 公式の資料でも、「許可のルールは、AI ではなく Claude Code が強制する。指示は、何を試すかに影響するが、何が許可されるかは変えない」と説明されている。

## 3. `Read(.env)` と `Read(/.env)` の違いは何か。M7 の `.env` を守るには、どちらを書くか。

**答えの例**: 拒否ルールの `Read(.env)`（`Read(./.env)`、`Read(**/.env)` も同じ）は、**どの深さの** `.env` にも効く。先頭が `/` の `Read(/.env)` は、**作業フォルダの直下**の `.env` だけに効く。M7 の `.env` は、`modules/m7-local-env/app/` の中にあるので、**`Read(.env)`（または `Read(**/.env)`）** を書く。`/` を付けると、`app/` の中の `.env` は、守れなくなる。

**押さえる点**
- 拒否ルールを書いたら、**効いているかを、実際に確かめる**。書き方のずれで、「守れていないのに、守れていると思い込む」ことが起きる（演習 2 で、別セッションを使って確かめた）。
- 許可（allow）ルールでは、同じ書き方でも、直下だけに効く場合がある（公式の資料）。許可と拒否で、効き方が違う。

## 4. コマンドの拒否ルール（例: `Bash(git push *)`）が、完全な壁でないのは、なぜか。それでも、確認画面を読む習慣が必要なのは、なぜか。

**答えの例**: コマンドの拒否は、**書かれた形**にだけ効くから。たとえば、`git -C . push` や、`bash -c 'git push'` のように、**形を変えれば**、同じ操作が、ルールをすり抜けることがある。そのため、拒否ルールは、「普通に頼んだとき」の防止であって、セキュリティの壁ではない。確認画面を読んで、**許可しない**判断が、最後の砦になる。さらに、隔離（サンドボックス、worktree）と、そもそも渡さない設計を、重ねる。

**押さえる点**: ファイルの読み取り拒否も、**スクリプトが自分でファイルを開く場合**には、効かない。

## 5. worktree で、AI に作業させる利点は何か。作業のあと、何を確かめ、どうするか。

**答えの例**: 手元の作業フォルダを、**汚さない**。変更が、別のブランチにまとまり、**気に入らなければ、まるごと捨てられる**。並行して、複数の作業を進められる。作業のあとは、**差分を読んで**、頼んだ範囲に収まっているかを確かめる。範囲外の変更があれば、取り消す（または捨てる）。気に入れば、ブランチをコミットして、**PR にして、CI とレビューを通す**。気に入らなければ、worktree とブランチを削除する。

**押さえる点**: 作業場所が別なので、`node_modules` や `.env` は、ありません。必要なら、そこで依存関係を入れる。

## 6. プロンプトインジェクションとは何か。AI が読む文章の中に、命令が紛れていたら、どうするか。

**答えの例**: AI が読む文章（Web ページ、Issue、他人の PR、ライブラリの説明文など）の中に、**命令が紛れていて**、AI が、それを、ユーザーの指示のように扱ってしまうこと。文章の中の命令は、**文章を書いた人**のもので、**あなたの指示ではない**。AI が、頼んでいない操作（ファイルの作成、コマンド、外部への送信）をしようとしたら、**確認画面で、許可しない**。信頼できない文章を、AI に、そのまま読ませない。

**押さえる点**: 命令は、**目に見えない場所**（コメントなど）にも書ける。だから、「見えるところに、何も書かれていない」ことは、安全の証拠にならない。

## 7. 危険な操作を見分ける観点を、3 つ挙げよ。

**答えの例**（3 つ以上）
- **取り消せるか**: 失敗したら、元に戻せるか（削除、強制 push、`git reset --hard` は、戻せない）。
- **範囲**: 影響が、頼んだ範囲を、超えないか（`docker system prune -a` は、他のプロジェクトにも及ぶ）。
- **外へ出るか**: データを、外部に送る・外から取り込んで実行するか（`git push`、`curl | bash`）。
- **秘密に触れるか**: `.env`、鍵、個人情報を、読む・書く・出力するか。
- **分かるか**: 自分が、そのコマンドを、説明できるか。

**押さえる点**: **分からないコマンドは、許可しない。** 迷ったときは、止まる側に倒す。

## 8. AI にコンフリクトを解消させたとき、何を確かめるか。

**答えの例**: **印が残っていない**こと（`git diff --check`）。**両方の変更の意図が残っている**こと（解消後の `git diff` を自分で読む。AI は、片方を黙って捨てることがある）。AI が実行するコマンドが**安全**であること（`git reset --hard`、全部を片方に寄せる操作、強制 push は許可しない）。解消のあとも、**テストと CI が通る**こと。どちらを残すかは、**人が決める**。

**押さえる点**: 「AI が解消した」ではなく、「**自分が内容を理解して確かめた**」と言える状態にする（M4 のレビューと同じ）。
