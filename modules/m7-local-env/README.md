# M7 手元の環境（ローカルの Supabase）

所要時間の目安: 準備 30〜60 分 ＋ 説明 20 分 ＋ 演習 70 分

> このモジュールは、M8（テストと E2E）・M9（セキュリティ）と**同じ題材**（`app/`）を使います。M7 で作った環境の上に、M8・M9 で積み上げていきます。
>
> `app/` には、M8 以降で使うファイル（`src/server.ts`、`test/`、`e2e/` など）も、すでに入っています。**M7 では、触りません。**

## 1. なぜ、手元で動かすのか

私たちのシステムは、実在の生徒・保護者の個人情報を扱います。開発のために、本物のデータベースに触れるわけにはいきません。

そこで、**自分のパソコンの中に、本物と同じ仕組みの小さなデータベースを用意**して、そこで開発します。

| 手元で動かす利点 | 説明 |
|---|---|
| **本番に触れない** | 本物のデータや、本物の鍵を使わない。間違えても、誰にも影響しない |
| **秘密が要らない** | 本物の鍵を、開発者が持たなくてよい |
| **何度でもやり直せる** | 壊しても、コマンド1つで初期状態に戻せる |
| **誰でも同じ状態を再現できる** | チームの全員が、同じ手順で、同じ環境を作れる |

## 2. 環境は、複数ある

| 環境 | 場所 | 目的 | データ |
|---|---|---|---|
| **手元（ローカル）** | 自分のパソコン | 開発・実験 | 架空のデータ |
| **staging（検証用）** | クラウド | 本番に近い状態での確認 | 架空のデータ |
| **本番** | クラウド | 実際の運用 | 実在の個人情報 |

環境の間で**仕組み（データベースの形など）がずれる**と、「手元では動いたのに、本番では動かない」事故が起きます。ずれを防ぐための道具が、次のマイグレーションです。

## 2b. データベースと SQL とは（先に知っておくこと）

> **SQL を、書けるようになる必要はありません。** 読んで、**何をしているか**が分かれば十分です。分からない文は、AI に、自分の言葉で質問します（M2）。

### データベースとテーブル

**データベース**は、データを整理して保管する仕組みです。データは、**テーブル（表）**に入れます。表計算ソフトの「シート」のようなものです。

| 用語 | 意味 | このコースの例（`notes` テーブル） |
|---|---|---|
| **テーブル** | データを入れる表 | `notes`（メモの表） |
| **列（カラム）** | 表の縦の項目。**名前と、入れてよい種類**が決まっている | `id`、`title`、`body`、`created_at` |
| **行（レコード）** | 表の横 1 件分のデータ | 「はじめてのメモ」の 1 件 |
| **主キー** | 行を、**1 件に特定する**ための列 | `id` |

### SQL とは

**SQL** は、データベースに**指示を出すための言葉**です。画面やアプリは、裏で SQL を使って、データの読み書きをしています。

| やりたいこと | SQL の例 | 意味 |
|---|---|---|
| **読む** | `select title from notes;` | `notes` から、`title` の列を取り出す |
| **足す** | `insert into notes (title) values ('新しいメモ');` | `notes` に、1 行を足す |
| **直す** | `update notes set title = '直した' where id = ...;` | 条件に合う行を、書き換える |
| **消す** | `delete from notes where id = ...;` | 条件に合う行を、消す |

- **`where`（条件）を付け忘れると、全部の行が対象になります。** 特に `update` と `delete` は、**取り消せない**ので、条件を確かめます。
- 上の 4 つは「**中のデータ**」を扱う指示です。一方、**表そのもの**（テーブルを作る、列を足す）を扱う指示もあります（`create table`、`alter table`）。次のマイグレーションは、こちらです。
- 実際の画面や API の裏の SQL は、AI や道具が作ります。**自分で書くより、読んで、意味を確かめる**ことが多くなります。

## 3. マイグレーションとシードデータ

### マイグレーション

**データベースの形（テーブルや列）の変更履歴**を、順番付きのファイルで管理する仕組みです。中身は、**SQL で書かれた、形を変える指示**です。

たとえば、このコースの最初のマイグレーション（`supabase/migrations/20261029000000_create_notes.sql`）には、次のような指示が書かれています。

```sql
create table public.notes (
  id uuid primary key default gen_random_uuid(),
  title text not null check (char_length(title) between 1 and 100),
  body text not null default '',
  created_at timestamptz not null default now()
);
```

「`notes` という表を作る。列は `id`（主キー）、`title`（必須。1〜100 文字）、`body`（既定は空）、`created_at`（既定は今の日時）」と読めます。

**なぜ、ファイルで管理するのか**: アプリのコードは Git で履歴が残りますが、**データベースの形は、Git の外にあります**。誰かが手でテーブルを変えると、**他の人の環境や本番と、形がずれます**。形の変更を**ファイルにして Git に入れる**ことで、全員の環境に、**同じ順番で、同じ変更**を当てられます。

- ファイル名の先頭の数字（日時）の順に、**1回ずつ**適用される。
- 適用済みのファイルは、**二度と実行されない**。
- だから、**一度どこかの環境に適用したファイルは、書き換えない。** 変更したいときは、新しいファイルを足す（演習 4 で体験します）。

### シードデータ

開発用の**架空のデータ**です。`db:reset` のたびに投入されます。本物のデータは、絶対に入れません。

## 4. 鍵（キー）の種類

| 鍵 | できること | 置き場所 |
|---|---|---|
| **anon（匿名）** | RLS のルールの範囲内でだけ、読み書きできる | ブラウザ側のコードにも置いてよい（誰でも見える前提） |
| **service_role** | RLS を**すべて迂回**できる。何でもできる | **サーバー側だけ。ブラウザには絶対に渡さない** |

RLS（行レベルセキュリティ）は、「どの人が、どの行を読み書きしてよいか」をデータベースの側で決める仕組みです。詳しくは M9 で扱います。
