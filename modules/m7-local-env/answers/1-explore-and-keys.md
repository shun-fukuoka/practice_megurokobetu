# M7-1 の答えと解説

> 先に、自分の予想と考えを書き残してから読んでください。

## 設問2〜4: 鍵の違いの結果

### ヒント

- anon の鍵は「RLS のルールに従う」鍵。ルールで許されていない操作は、拒否される。
- service_role の鍵は「RLS を迂回する」鍵。

### 答え

| 鍵 | 追加の結果 | 表示 |
|---|---|---|
| anon（匿名） | **失敗** | `new row violates row-level security policy for table "notes"` |
| service_role | **成功** | 追加され、`npm run notes` で 6 件になる |

## 設問5: 原因の行

`20261029000000_create_notes.sql` には、次の2つが書かれています。

```sql
alter table public.notes enable row level security;     -- RLS を有効にする

create policy "notes are readable by everyone"
  on public.notes
  for select                                            -- 許可するのは「読む」だけ
  using (true);
```

RLS を有効にすると、**ポリシーで許された操作だけ**ができます。許可したのは `select`（読む）だけで、`insert`（追加）を許可するポリシーは無いので、匿名の鍵では追加が拒否されます。

## service_role の鍵が、ブラウザのコードに入っていたら

ブラウザに送られるコードは、**そのサイトを開いた誰でも読めます**（開発者ツールで見られる）。service_role の鍵が入っていれば、誰でもその鍵を取り出し、RLS を無視して、**すべてのデータを読み、書き換え、削除できる**ようになります。個人情報の漏えいや、データの破壊に直結します。

だから、service_role の鍵は、**サーバー側のコードだけ**で使います。

## 振り返りの答え

- **anon と service_role**:
  - anon: RLS のルールの範囲でだけできる。ブラウザ側のコードに置いてもよい（誰でも見える前提で、ルールで守る）。
  - service_role: RLS を迂回して何でもできる。サーバー側だけに置く。
- **ローカルの鍵が「秘密ではない」のに気をつける理由**: ローカルの鍵は誰のパソコンでも同じデモ用の値なので、漏れても実害はない。しかし、**本番の鍵を扱うときと同じ習慣**（コードに直接書かない、`.env` を Git に入れない、必要な場所にだけ置く）を、ここで身につけておくため。習慣は、本番で急に切り替えられない。
