# M7-2 の答えと解説

> 先に、自分の予想と考えを書き残してから読んでください。

## 設問2〜4: 結果

### ヒント

- `db:reset` は、データを「直す」のではなく、「作り直す」。
- 作り直すとき、何のファイルが使われるか。`supabase/` フォルダの中身を見る。

### 答え

| 操作 | 結果 |
|---|---|
| データをすべて削除したあと | `npm run notes` → 0 件 |
| `npm run db:reset` のあと | **5 件**に戻る |
| 自分で足したメモ | `db:reset` のあとは**消える** |

`db:reset` は、データベースを**一から作り直して**、`supabase/migrations/` のマイグレーションを順に適用し、そのあと `supabase/seed.sql` のデータを入れます。だから、マイグレーションとシードに書かれていないものは、すべて消えます。

## 設問5: 考える

### 自分で足したメモが消えるのは、困ることか

**利点です。** ローカルの環境は「使い捨て」で、何がどうなっているかは、ファイル（マイグレーションとシード）が決めます。手元で積み重なった、よく分からない状態に依存せずに済みます。残したいデータがあるなら、`seed.sql` に書きます（そうすれば、チーム全員が同じになります）。

### 全員が同じテスト用データを持つ利点

- 「自分の環境では動いた」「私の環境では動かない」が減る（再現性）。
- 他の人のバグ報告を、同じ状態で再現できる。
- 自動のテスト（M8）が、毎回同じ前提で動ける。

### 実在の人の名前やメールアドレスを、シードに入れてはいけない理由

- `seed.sql` は **Git に入り、チームの全員（と、履歴）に共有される**。個人情報が複製されてしまう。
- 一度コミットすると、履歴に残り、後から消しても「漏れた」扱いになる（M4 の秘密と同じ）。
- 開発の目的に、本物のデータは**必要ない**。

## 振り返りの答え

- **`db:reset` が行うこと**: ローカルのデータベースを破棄し、マイグレーションとシードから**作り直す**。
- **本番のデータベースで同じことをしたら**: 実在のデータがすべて失われる。**本番では、絶対にしない。** ローカルだから気軽にできる、という違いが、ローカル環境の価値そのもの。
