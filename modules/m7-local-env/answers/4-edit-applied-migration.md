# M7-4 の答えと解説

> 先に、自分の予想と考えを書き残してから読んでください。

## 設問3〜5: 結果

### ヒント

- `db:migrate` は「まだ適用していないファイルだけ」を適用する。
- `db:reset` は「全部を、一から」適用する。

### 答え

| | `pinned` 列 |
|---|---|
| 書き換える前から動いていたデータベース（手順 3 のあと） | **なし**（`db:migrate` は何も適用しない: 書き換えたファイルは「適用済み」として扱われる） |
| `db:reset` で作り直したデータベース（手順 4 のあと） | **あり**（一から全ファイルを適用するので、書き換えた内容が入る） |

**同じマイグレーションのファイルから、形の違うデータベースができてしまいました。** しかも、どちらも**エラーは出ません**。

## 設問6: 考える

### staging や本番が「書き換える前から動いていたデータベース」だったら

- 本番には `pinned` 列が**できない**。
- 手元（`db:reset` で作り直した環境）では動くコードが、本番では「列が存在しない」エラーで**壊れる**。
- 原因が分かりにくい。ファイルを見ると、列は定義されているように見える。

### 正しいやり方

書き換えたものを**元に戻し**、`pinned` 列を足す**新しいマイグレーション**を作る（演習 3 と同じ）。

```sql
alter table public.notes add column pinned boolean not null default false;
```

## 振り返りの答え

- **「静かに」起きることの危険**: エラーが出ないので、気づくのが遅れる。気づいたときには、本番とのずれが蓄積していて、原因の特定も修正も難しい。「ずれ」は、見つかるまで確実に残る。
- **機械で検出する仕組み**: たとえば、
  - すでに main に入っているマイグレーションのファイルが変更されていないかを、CI で検査する
  - 本番に適用済みの履歴と、ファイルの履歴を突き合わせる
  - いずれも、**人の注意に頼らず、仕組みで防ぐ**という M4 の考え方につながる。CI のコース（後で作成予定）で扱う候補。
