# 演習 M7-4: 適用済みのファイルを書き換えてみる

所要時間の目安: 20 分 / 前提: [演習 3](3-add-migration.md)（片づけの確認まで終えていること）

## 目的

「適用済みのマイグレーションは書き換えない」というルールの**理由を、体験で理解する**。

> 状況の見立て: 「今のデータベース」は、すでにマイグレーションを適用済みの環境（staging や本番に相当）です。「`db:reset` で作り直したデータベース」は、友達が新しく作った環境に相当します。

## 手順

作業は `modules/m7-local-env/app` の中で行います。

### 0. 記録の Issue を作り、予想を書く

[演習の進め方（M0 の 3b）](../../m0-orientation/README.md)に従い、「演習の記録」の Issue（演習: `M7-4`）を作ります。次の予想を、**実行する前に**書いてください。

適用済みの `supabase/migrations/20261029000000_create_notes.sql` を書き換えて、列を足したとき:

- 今のデータベース（すでに適用済み）に、列は増えるか。
- `db:reset` で作り直したデータベースには、列は増えるか。
- この2つが食い違うと、どんな問題が起きそうか。

### 1. 始める前の状態を確かめる

```bash
git status
```

変更が出ないこと（演習 3 の片づけが済んでいること）を確認します。**これが、片づけで戻す状態です。**

### 2. 書き換える

`20261029000000_create_notes.sql` の `body text not null default '',` の行の次に、次の1行を足します。

```sql
  pinned boolean not null default false,
```

### 3. 今のデータベースに反映してみる

```bash
npm run db:migrate
```

表示を確認します。そのあと、Studio の **Table Editor** で `notes` を開き、見出しに `pinned` 列があるかを確認します（画面を再読み込みしてから見ます）。

### 4. 作り直したデータベースを見る

```bash
npm run db:reset
```

Studio の **Table Editor** で `notes` を開き（再読み込みしてから）、`pinned` 列があるかを確認します。

### 5. 食い違いを整理する

次の表を埋めて、記録の Issue のコメントに書きます。

| | `pinned` 列 |
|---|---|
| 書き換える前から動いていたデータベース（手順 3 のあと） | あり／なし |
| `db:reset` で作り直したデータベース（手順 4 のあと） | あり／なし |

### 6. 考える

- 実際の開発で、staging や本番が「書き換える前から動いていたデータベース」だったら、何が起きるか。
- 正しいやり方は何だったか。

### 7. 片づけ

`20261029000000_create_notes.sql` に足した 1 行を**元に戻し**、データベースを作り直します。

```bash
npm run db:reset
```

**片づけの確認**:

```bash
git status
git diff supabase/migrations
```

どちらも**何も表示されない**こと。Studio で `pinned` 列が無いことも確認します。

## 振り返り

- この食い違いを、機械で検出する仕組みがあるとしたら、どんなものか。
