# M7 確認の質問の答えと解説

> 先に、自分の言葉で答えを考えてから読んでください。答えは 1 つではありません。

## 1. ローカルで動かす利点を、3 つ挙げられるか。

**答えの例**（3 つ以上、挙げられればよい）
1. **本番に触れない**: 本物のデータや鍵を使わない。間違えても、誰にも影響しない。
2. **秘密が要らない**: 本物の鍵を、開発者が持たなくてよい。
3. **何度でもやり直せる**: 壊しても、`db:reset` で初期状態に戻せる。
4. **誰でも同じ状態を再現できる**: チームの全員が、同じ手順で、同じ環境を作れる。

**押さえる点**: 利点は、「便利」だけでなく、**安全（本番に触れない）と再現性**にある。

## 2. 適用済みのマイグレーションを書き換えてはいけないのは、なぜか。

**答えの例**: マイグレーションは、**1 回ずつ、日時の順に適用**され、適用済みのものは**二度と実行されない**。適用済みのファイルを書き換えても、**すでに適用済みの環境（staging や本番）には反映されず**、新しく作り直した環境にだけ反映される。同じファイルから、**形の違うデータベース**ができ、しかも**エラーが出ない**。手元では動いて、本番では壊れる、という事故になる。変更したいときは、**新しいマイグレーションを足す**。

**押さえる点**
- 「静かに」食い違う危険（エラーが出ないので、気づくのが遅れる）。
- 「履歴」として並べて管理する、という考え方（Git がコードの履歴を残すのと同じ）。

## 3. `service_role` の鍵を、ブラウザ側のコードに置いてはいけないのは、なぜか。

**答えの例**: ブラウザに送られるコードは、そのサイトを開いた**誰でも読める**（開発者ツールで見られる）。`service_role` の鍵は、RLS（行レベルセキュリティ）を**すべて迂回**して、何でも読み、書き、削除できる。ブラウザのコードに入っていれば、誰でもその鍵を取り出し、**すべてのデータを読み書き・削除**できてしまう。個人情報の漏えいや、データの破壊に直結する。サーバー側だけで使う。

**押さえる点**
- anon の鍵は、RLS のルールの範囲でだけ動くので、ブラウザに置いても、ルールで守られる（誰でも見える前提）。
- ローカルの鍵が秘密でなくても、**本番と同じ扱いの習慣**をつける。

## 4. データベース、テーブル、列、行を、`notes` を例に説明できるか。SQL とは何か。

**答えの例**: データベースは、データを整理して保管する仕組みで、データは**テーブル（表）**に入れる。`notes` テーブルなら、**列**が `id`・`title`・`body`・`created_at` という項目で、**行**がメモ 1 件分。**SQL** は、データベースに指示を出す言葉で、読む（`select`）、足す（`insert`）、直す（`update`）、消す（`delete`）ができる。表そのものを作る・変える指示（`create table`、`alter table`）もある。

**押さえる点**
- SQL を書ける必要はなく、**読んで、何をしているか**が言えればよい。
- `update` と `delete` は、`where` を付け忘れると**全部の行**が対象になる。取り消せない。

## 5. マイグレーションとは何か。形の変更を、手で直さずにファイルで管理するのは、なぜか。

**答えの例**: データベースの**形（テーブルや列）の変更履歴**を、SQL で書いた、**順番つきのファイル**で管理する仕組み。データベースの形は Git の外にあるので、手で直すと、**他の人の環境や本番と、ずれる**。ファイルにして Git に入れれば、**全員の環境に、同じ変更を、同じ順番で当てられ**、いつ誰が何を変えたかも残る。

**押さえる点**: 「コードは Git にあるが、データベースの形は別」という点が出発点。**適用済みのファイルは書き換えず、新しいファイルを足す**（演習 4）。
