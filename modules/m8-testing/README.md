# M8 テストと E2E

所要時間の目安: 準備 20〜30 分 ＋ 説明 20 分 ＋ 演習 90 分

> このモジュールは、M7 と**同じ題材**（`modules/m7-local-env/app/`）を使います。M7 で動かした Supabase の上に、小さな Web 画面と、3 種類のテストを使います。M9（セキュリティ）でも、この画面を使います。

## 1. なぜ、テストを書くのか

コードを変更するたびに、「前から動いていたものを、壊していないか」を確かめる必要があります。

- 人が毎回、すべての画面を手で確かめるのは、時間がかかるうえ、必ず漏れが出る。
- AI が書いた変更は、意図しないところまで書き換えることがある（M4-3 で見たとおり）。
- 自動のテストは、**確かめ方を、機械が覚えておいてくれる**。何度でも、同じように確かめられる。

テストは、「壊していない**証拠**」です。ただし、証拠が書かれているのは、**テストが確かめたことだけ**です。

## 2. テストの種類

このコースの題材には、3 種類のテストがあります。

| 種類 | 場所 | 確かめること | 必要なもの | 速さ（目安） |
|---|---|---|---|---|
| **単体テスト** | `test/unit/` | 1 つの関数の、入力と結果（例: タイトルの検証） | なし | ミリ秒 |
| **DB のテスト** | `test/db/` | データベースの設定（例: 匿名の鍵では追加できない） | ローカルの Supabase | 0.1 秒前後 |
| **E2E テスト** | `e2e/` | 本物のブラウザで、人の操作を再現（例: 追加ボタンを押すと一覧に出る） | ローカルの Supabase とブラウザ | 数十秒 |

> E2E は、「エンドツーエンド」（端から端まで）の略です。画面から、サーバー、データベースまで、全体を通して確かめます。

### どれを、どれだけ書くか

```
        ／＼        E2E: 少なく。重要な操作だけ
       ／  ＼       DB のテスト: 設定やルールが壊れていないか
      ／────＼
     ／ 単体   ＼   単体テスト: 多く。速く、原因が分かりやすい
    ／──────────＼
```

- **速くて原因が分かりやすい**ものを、たくさん書く（単体テスト）。
- **遅くて壊れやすい**ものは、本当に重要な操作に絞る（E2E）。
- E2E で見つけた問題は、できれば、より小さなテスト（単体や DB）で再現できるようにしておく。

## 3. 何を、テストするか

- **壊れると困るもの**（個人情報の扱い、権限）
- **過去に壊れたもの**
- **境界**（ちょうど 100 文字、空、前後の空白など。間違いが起きやすい）
- **設定やルール**（M7 の RLS のように、コードを書かない部分でも、テストにできる）

## 4. テストの落とし穴

| 落とし穴 | 説明 |
|---|---|
| **通る＝正しい、ではない** | テストが確かめていないことは、壊れていても気づけない（演習 1） |
| **テストを弱めて通す** | `skip` にする、期待値を書き換える。問題を隠すだけで、直していない（M4-3） |
| **テスト同士が依存する** | 順番や、前のテストの影響で、結果が変わる（演習 4） |
| **不安定（flaky）** | 同じコードなのに、通ったり落ちたりする。信用されなくなり、無視される |
| **遅すぎる** | 遅いと、実行されなくなる |

## 5. 準備

1. M7 の準備（[SETUP.md](../m7-local-env/SETUP.md)）が終わっていて、`.env` に**3 つの値**（`SUPABASE_URL`、`SUPABASE_ANON_KEY`、`SUPABASE_SERVICE_ROLE_KEY`）があること。
2. ローカルの Supabase を起動する。

   ```bash
   cd modules/m7-local-env/app
   npm ci
   npm run db:start
   ```

3. E2E 用のブラウザ（Chromium）を、**1 回だけ**取得する。数百 MB あるので、時間がかかります。

   ```bash
   npx playwright install chromium
   ```

4. 動作確認として、単体テストを実行する。

   ```bash
   npm run test:unit
   ```

   「6 pass」と出れば、準備は完了です。

## 8. AI とテスト

AI にテストを書かせることは、よくあります。次の点に気をつけてください（[M2](../m2-ai-learning/README.md)）。

- AI が書いたテストは、**通るかどうか**ではなく、**コードを壊したら落ちるか**で確かめる（演習 1 の手順）。
- テストを通すために、**テストを書き換えさせない**。
- 重要な部分（権限、個人情報）のテストは、人が内容を読む。

## 9. 確認（面談）

- 単体テスト、DB のテスト、E2E の違いを、「速さ」と「見つけられるもの」で説明できるか。
- 「テストが全部通っているから安全」と言えないのは、なぜか。
- E2E を、むやみに増やさないのはなぜか。
- テストが、前のテストの結果に依存すると、何が困るか。
