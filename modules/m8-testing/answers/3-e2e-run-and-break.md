# M8-3 の答えと解説

> 先に、自分の予想と考えを書き残してから読んでください。

## 設問: 3 つのテストと、予想

### ヒント

- 3 つのうち、「追加」ボタンを**押している**テストは、どれか。
- 一覧を**見るだけ**のテストは、ボタンを押すか。

### 答え

`e2e/notes.spec.ts` の 3 つのテスト:

| テスト | 再現している人の操作 | ボタンを「送信」に変えたとき |
|---|---|---|
| 初期データが、一覧に表示される | ページを開いて、一覧を見る | **通る**（ボタンを使わない） |
| メモを追加すると、一覧に表示される | タイトルを入力して、「追加」を押し、一覧を見る | **失敗する** |
| タイトルが空だと、エラーが表示される | 何も入力せず「追加」を押し、エラーを見る | **失敗する** |

## 手順 4: 失敗の読み方

失敗したテストのメッセージは、次の形です。

```
TimeoutError: locator.click: Timeout 5000ms exceeded.
  - waiting for getByRole('button', { name: '追加' })
```

読み方: 「**『追加』という名前のボタンを探して待ったが、5 秒たっても見つからなかった**」。

| 証拠 | 場所 | 分かること |
|---|---|---|
| スクリーンショット | `test-results/…/test-failed-1.png` | 失敗した瞬間の、画面の見た目（ボタンが「送信」になっている） |
| 操作の記録 | `test-results/…/trace.zip` | 各操作の前後の画面と、ページの状態を、順に追える |
| 失敗の状況のまとめ | `test-results/…/error-context.md` | 失敗したときの状況をまとめた文書（実行すると作られる。中身は、自分で開いて確かめる） |

まず、**メッセージを読み、スクリーンショットを見る**と、たいていの原因が分かります。

## 手順 5: 考える

### 「バグを見つけた」のか、「テストが壊れやすい」のか

**両方の面があります。**

- ボタンの文言は、利用者にとっては**意味のある変更**です。以前の「追加」を探していた操作は、もう通用しません。テストが失敗したのは、「利用者が見る画面が変わった」ことを、正しく検出した、とも言えます。
- 一方で、文言の修正のたびにテストを直す必要があるのは、**E2E の維持コスト**です。

### 「役割と名前」で探す利点

- 画面の**見た目の位置**（何番目の要素か）で探すと、デザインの変更で、すぐ壊れる。
- 「ボタンで、名前が『追加』」で探すと、**利用者から見て、同じ意味のもの**を探せる。見た目が変わっても、意味が同じなら、通る。
- また、画面の読み上げソフトが使う情報（アクセシビリティ）と同じ見方なので、アクセシビリティの確認にもつながる。

## 振り返りの答え

- **E2E が遅い理由**: 本物のブラウザを起動し、ページを開き、サーバーとデータベースを通して、画面の描画を待つ。単体テストは、関数を呼ぶだけ。
- **むやみに増やさない理由**: 遅い。壊れやすい（文言、画面の変更、タイミング）。原因の特定が難しい。そのため、**本当に重要な操作**（追加できる、エラーが出る）に絞り、細かいルールは、単体テストで確かめる。
