# 演習 M8-1: 単体テストの「穴」を見つける

所要時間の目安: 25 分 / 前提: [README](../README.md) の準備（単体テストが 6 件通ること）

## 目的

テストが全部通っていても、**確かめていないことは、壊れても気づけない**ことを体験する。

## 手順

作業は `modules/m7-local-env/app` の中で行います。

### 0. 記録の Issue を作り、予想を書く

[演習の進め方（M0 の 3b）](../../m0-orientation/README.md)に従い、「演習の記録」の Issue（演習: `M8-1`）を作ります。次の予想を、**実行する前に**書いてください。

- `src/notes.ts` の `validateTitle` を読み、タイトルの長さのルールを、自分の言葉で書く。
- 「101 文字以上でエラー」のはずの条件を、わざと「100 文字以上でエラー」に変えると、既存の単体テストのうち、いくつが失敗するか。

### 1. 始める前の状態を確かめる

```bash
git status
npm run test:unit
```

`git status` に変更が出ないこと、テストが「6 pass」になることを確認します。

### 2. 既存のテストを読む

`test/unit/notes.test.ts` の、`validateTitle` のテスト（3 件）を読みます。**100 文字や 101 文字を確かめているテストはありますか。**

### 3. バグを仕込む

`src/notes.ts` の次の行を、書き換えます。

```ts
// 変更前
if (title.length > TITLE_MAX) {
// 変更後（ちょうど 100 文字でも、エラーにしてしまう）
if (title.length >= TITLE_MAX) {
```

### 4. 既存のテストを実行する

```bash
npm run test:unit
```

結果を、記録の Issue のコメントに書きます（予想と、合っていましたか）。

### 5. 穴を埋めるテストを足す

`test/unit/notes.test.ts` の、`validateTitle` のテストの下に、次の 2 件を足します。

```ts
test("100 文字のタイトルは受け付ける", () => {
  assert.equal(validateTitle("あ".repeat(100)).ok, true);
});

test("101 文字のタイトルは、エラーになる", () => {
  assert.equal(validateTitle("あ".repeat(101)).ok, false);
});
```

もう一度、実行します。

```bash
npm run test:unit
```

どのテストが失敗しましたか。

### 6. バグを直す

`>=` を `>` に戻して、もう一度実行します。8 件がすべて通ることを確認します。

### 7. 考える

- 手順 4 で、バグがあるのに、テストが通ったのはなぜか。
- AI に「この関数のテストを書いて」と頼んで、出てきたテストが全部通った。それだけで、テストが十分と言えるか。どう確かめればよいか。

### 8. 片づけの確認

足した 2 件のテストは、**残して構いません**（良いテストです）。次を確認します。

```bash
git diff src
npm run test:unit
```

`git diff src` に**何も表示されない**（バグを戻せている）こと、テストが「8 pass」になること。

## 振り返り

- 「境界」とは何か。なぜ、間違いが起きやすいのか。
- テストが「通る」ことと、「十分である」ことは、どう違うか。
