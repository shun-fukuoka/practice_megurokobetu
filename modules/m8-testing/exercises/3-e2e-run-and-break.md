# 演習 M8-3: E2E を動かして、壊す

所要時間の目安: 25 分 / 前提: [README](../README.md) の準備（Chromium の取得を含む）、ローカルの Supabase が起動していて、`.env` が設定済みであること

## 目的

- E2E が、本物のブラウザで人の操作を再現する様子を見る。
- 画面を変えたときに、E2E が**どう失敗し、どう読めばよいか**を体験する。

## 手順

作業は `modules/m7-local-env/app` の中で行います。

### 0. 記録の Issue を作り、予想を書く

[演習の進め方（M0 の 3b）](../../m0-orientation/README.md)に従い、「演習の記録」の Issue（演習: `M8-3`）を作ります。次の予想を、**実行する前に**書いてください。

- `e2e/notes.spec.ts` を読み、3 つのテストが、それぞれ人のどんな操作を再現しているかを書く。
- `src/notes.ts` の「追加」ボタンの文言を「送信」に変えると、3 つのうち、どのテストが失敗するか。

### 1. 始める前に、初期状態にする

```bash
npm run db:reset
git status
```

`git status` に変更が出ないことを確認します。

### 2. E2E を実行する

```bash
npm run test:e2e
```

3 件が通ることを確認します。かかった時間を書き留めます（`npm run test:unit` とくらべてください）。

次に、ブラウザの動きを**目で見る**実行をします。

```bash
npx playwright test --headed
```

ブラウザが開き、入力や押下が自動で行われます。

### 3. 画面を変える

`src/notes.ts` の、次の行を変えます。

```html
<!-- 変更前 -->
<button type="submit">追加</button>
<!-- 変更後 -->
<button type="submit">送信</button>
```

### 4. E2E を実行する

```bash
npm run test:e2e
```

結果を、記録の Issue のコメントに書きます（予想と、合っていましたか）。そのうえで、失敗したテストについて、次を読み取ってください。

- エラーメッセージ（何を探して、見つからなかったのか）
- `test-results/` フォルダの中の、失敗時のスクリーンショット（`test-failed-1.png`）
- 操作の記録（`trace.zip`）。`npx playwright show-trace` に、`trace.zip` のパスを渡すと、操作を順に見られる

### 5. 考える

- ボタンの文言を変えただけで、E2E が失敗した。これは「バグを見つけた」のか、「テストが壊れやすい」のか。
- E2E の探し方（`getByRole("button", { name: "追加" })`）は、画面の「見た目の位置」ではなく、「役割と名前」で探している。これには、どんな利点があるか。

### 6. 元に戻す

「送信」を「追加」に戻し、もう一度実行して、3 件が通ることを確認します。

**片づけの確認**:

```bash
git diff src
```

何も表示されないこと。

## 振り返り

- E2E が、単体テストにくらべて遅いのは、なぜか。
- E2E を、むやみに増やさないほうがよいのは、なぜか。
