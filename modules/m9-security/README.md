# M9 セキュリティ

所要時間の目安: 準備 15 分 ＋ 説明 25 分 ＋ 演習 120 分

> このモジュールは、M7・M8 と**同じ題材**（`modules/m7-local-env/app/`）を使います。M7 の環境（ローカルの Supabase と `.env`）が、準備済みであることが前提です。
>
> **攻撃や防御の実技は、できなくて構いません。コードも、書きません。** 目的は、**「どの経路が、弱点になるか」「なぜ、その対策が必要か」を、自分の言葉で説明できる**ことです。ブラウザの開発者ツールと、手順書の短い文を使って、**観察して、壊して、理解**します。

## 1. このモジュールの狙い

私たちが扱うのは、生徒・保護者・講師の**個人情報**です。誰が、何を、見て・変えてよいかを、**サーバーが確実に守る**必要があります。

画面の見た目（ボタンを隠す、入力欄を出さない）は、**守りにはなりません**。画面は、利用者のブラウザの中にあり、利用者が自由に操作できるからです。**守るのは、サーバー**です。

## 2. 深さは、レベルで変えます

| テーマ | L0（全員） | L2（機能担当） |
|---|---|---|
| 個人情報・秘密を守る（M0・M5・M7 の復習） | **理由を説明できる** | 同左 |
| 画面に文字を出すときの危険（XSS） | **入口：何が起きるかを、説明できる** | 対策（エスケープ）と、HttpOnly の位置づけを説明できる |
| 認証（ログイン）と Cookie | 概念 | **Cookie の仕組みと属性、サーバーで確かめる理由を説明できる** |
| 認可（誰に、何を許すか） | 概念 | **認証との違い、フォームの値を信じない理由を説明できる** |
| ブルートフォース・ボット対策 | 概念 | **レート制限と、CAPTCHA（Turnstile）の役割を説明できる** |

L0 は、演習 1・4 と、「確認」の一部を、重点的に行います。L2 は、全部を行います。

## 3. 攻撃者の入口の地図

「どの経路から、何が漏れるか」を、地図にします。

| 入口 | 起こりうること | 主な対策 | 演習 |
|---|---|---|---|
| **画面の裏の API**（画面を使わず、直接呼ぶ） | ログインなしで、データを追加・取得される | サーバーで、**認証と認可を確かめる** | 1・3 |
| **Cookie** | 盗まれると、**本人になりすまされる** | HttpOnly、SameSite、Secure、有効期間 | 2 |
| **権限** | 一般の利用者が、講師の操作をする | **サーバーが確かめた役割**で判断する。フォームの値は信じない | 3 |
| **画面に出す文字** | 悪意のあるスクリプトが、画面で実行される（XSS） | **エスケープ**、HttpOnly（被害の限定） | 4 |
| **ログイン** | パスワードを、機械的に何度も試される | レート制限、ボット対策（CAPTCHA）、失敗の理由を伝えない | 5 |
| **秘密・個人情報** | 漏えい | 渡さない、読ませない、コミットしない（M0・M4・M5・M6・M7） | 復習 |
| **依存パッケージ・自動化（CI）** | 悪意のあるコードが入る | 見知らぬ依存を入れない、CI は秘密を持たない（M4・M5） | 復習 |
| **AI** | 文章の中の命令に従う | 確認画面、拒否ルール（M6） | 復習 |

**対策は、1 つでは足りません。** どれか 1 つが破られても、次で止まるように、**層を重ねます**（多層防御）。

## 4. 基本の考え方

### 認証と認可は、別

| | 意味 | 問い | 例 |
|---|---|---|---|
| **認証** | **誰か**を、確かめる | あなたは、誰ですか | ログイン（メールアドレスとパスワード） |
| **認可** | **何をしてよいか**を、判断する | あなたは、これをしてよいですか | 講師だけが、メモを追加できる |

ログインできた人が、何でもできるわけではありません。**認証のあとに、認可がある**ことを、忘れないでください。

### サーバーで確かめる

- 画面から送られてくる値は、**利用者が、自由に書き換えられます**。たとえば、フォームに `role=teacher` を足して送ることも、できます。
- だから、**役割（role）などは、サーバーが「確かめた情報」から取り**、画面から送られた値は、**信じません**。

### Cookie とは

ブラウザが、**同じサイトへのリクエストのたびに、自動で送る、小さなデータ**です。ログインの状態（セッション）を、これで保ちます。**Cookie を盗まれると、本人になりすませる**ので、守る必要があります。

| 属性 | 意味 | 防ぐもの |
|---|---|---|
| **HttpOnly** | JavaScript から**読めない**（ブラウザは、送るだけ） | XSS で、Cookie を**読み取られる**こと |
| **SameSite=Lax** | **他のサイトから**送られるリクエスト（フォームの送信など）には、Cookie を付けない | 他のサイトに仕込まれた操作（CSRF） |
| **Secure** | **HTTPS の通信だけ**で送る | 通信の途中で、盗み見られること（ローカルの http では、付けない） |
| **Max-Age / Expires** | 有効期間 | 古い Cookie を、使い続けられること |

### XSS とは

画面に出す文字の中に、**悪意のあるスクリプトが紛れていて、それが利用者のブラウザで実行される**攻撃です。たとえば、メモのタイトルに、スクリプトを書いておくと、**そのメモを見た人のブラウザで、実行**されます。

- **主な対策は、エスケープ**です。画面に出す文字の、特殊な記号（`<`、`>`、`"`）を、「ただの文字」に置き換えます。
- **HttpOnly は、被害を限定します**（Cookie を、読み取らせない）。ただし、**XSS そのものは、防ぎません**。スクリプトは、利用者になりすまして、**操作**することは、できてしまいます。だから、エスケープが、第一の対策です。

### ブルートフォースと、ボット対策

- **ブルートフォース**: パスワードを、機械的に、何度も試す攻撃。
- **レート制限**: 短時間に、失敗が続いたら、受け付けない。対策の基本。
- ただし、**攻撃者が、たくさんの場所（IP アドレス）から試す**と、1 か所あたりの回数は、少なくなり、レート制限だけでは、防ぎきれません。
- **CAPTCHA（Turnstile など）**: **人間か、機械か**を確かめる仕組み。

  **Turnstile の流れ**
  1. 画面に、ウィジェット（公開されたサイトキーを使う）が表示される。
  2. ブラウザが、**1 回限りのトークン**を受け取る。
  3. ログインのリクエストに、そのトークンを添えて、サーバーに送る。
  4. **サーバー（または、認証の仕組み）が、秘密の鍵で、トークンを検証**する。**サーバー側で検証する**のが、大切。
  - 機械的な大量の試行を、**難しく、コストの高いもの**にする。完全ではないので、レート制限など、**他の対策と重ねる**。
  - （この演習の題材には、Turnstile は入っていません。外部のサービスの鍵が必要なためです。仕組みを、説明できることが目標です。）

### エラーメッセージで、教えすぎない

ログインの失敗で、「このメールアドレスは、登録されていません」と伝えると、**そのメールアドレスのアカウントが、あるかどうか**を、攻撃者に教えてしまいます。**「メールアドレスまたはパスワードが正しくありません」と、一律に伝える**のが、基本です。

## 5. 題材のアプリ

`modules/m7-local-env/app/` に、**2 つのサーバー**があります。

| | ログインなし | **ログイン付き** |
|---|---|---|
| 起動 | `npm run dev` | `npm run dev:secure` |
| 場所 | http://127.0.0.1:3100 | http://127.0.0.1:3101 |
| 使うモジュール | M8（E2E の対象） | **M9** |
| 誰でも追加できるか | **できる（穴がある）** | ログインした**講師だけ** |

ログイン付きのサーバーが、守っていること（すべて、**サーバー側**）は、次のとおりです。

1. **認証**: セッションの Cookie を、サーバーが、認証の仕組み（Supabase Auth）に確かめる。
2. **認可**: 役割は、確かめたユーザー情報から取る。フォームの値は、信じない。
3. **Cookie**: HttpOnly、SameSite=Lax。
4. **ブルートフォース対策**: 1 分間に 5 回、ログインに失敗したら、受け付けない。
5. **XSS 対策**: 画面に出す文字は、すべてエスケープする。
6. **失敗の理由を、伝えすぎない**。

これらは、**テスト**（`npm run test:secure`）でも守られています（M8 の考え方）。

## 6. 準備

1. M7 の準備（[SETUP.md](../m7-local-env/SETUP.md)）が終わっていて、ローカルの Supabase が起動していること。
2. 自分のターミナルで、次を実行します。

   ```bash
   cd modules/m7-local-env/app
   npm ci
   npm run seed:users
   ```

   演習用の、2 人のテストユーザー（講師と生徒）が作られます。

   | メールアドレス | 役割 | パスワード |
   |---|---|---|
   | `teacher@test.local` | teacher（講師） | `practice-pass-123` |
   | `student@test.local` | student（生徒） | `practice-pass-123` |

   > どちらも、**自分のパソコンの中だけの、架空のユーザー**です。このパスワードは、ローカル専用の、演習用の値です（本物のパスワードではありません）。
   > `npm run db:reset` で、データベースを作り直すと、ユーザーも消えるので、`npm run seed:users` を、もう一度実行します。

3. ブラウザの**開発者ツール**を、開けるようにしておきます（Chrome や Edge では、F12 キー）。

## 8. 確認（面談）

- 認証と認可の違いを、例で説明できるか。「画面でボタンを隠せば十分」と言えないのは、なぜか。
- Cookie とは何か。盗まれると、何が起きるか。HttpOnly と SameSite は、それぞれ何を防ぐか。
- XSS とは何か。主な対策は何か。HttpOnly は、XSS を防ぐのか。
- ログインの失敗で、「このメールアドレスは、登録されていません」と伝えてはいけないのは、なぜか。
- ブルートフォースとは何か。レート制限だけでは、足りないことがあるのは、なぜか。Turnstile のような仕組みは、何をして、どう動くか。
- 役割（role）を、フォームから送られた値ではなく、サーバーが確かめた情報から取るのは、なぜか。
- 「どの経路が、弱点になるか」を、3 つ挙げ、それぞれの対策を説明できるか。
- 個人情報と秘密を守るために、これまでのモジュールで学んだ仕組みを、3 つ挙げられるか。
