# M9-5 の答えと解説

> 先に、自分の予想と観察を書き残してから読んでください。失敗の回数と制限の動きは、教材の作成時に、自動テストと `curl` で、実際に確かめています。画面（ブラウザ）での操作は、確認していません。

## 観察の結果

### ヒント

- このサーバーは、**1 分間に 5 回**、ログインに失敗したら、受け付けなくする。

### 答え

| 回 | 結果 |
|---|---|
| 1〜5 回目（間違ったパスワード） | 毎回、「**メールアドレスまたはパスワードが正しくありません。**」（HTTP 401） |
| **6 回目** | 「**ログインの失敗が続いたため、しばらく受け付けません。…**」（HTTP **429**: 試行が多すぎる） |
| そのあと、**正しいパスワード** | **それでも受け付けない**（429）。制限が解けるまで、入れない |
| 1 分待つ、または、サーバーを再起動 | 制限が解け、**正しいパスワードで、ログインできる**（記録は、メモリの上だけなので、再起動で消える） |

### 存在しないメールアドレスのとき

存在するメールアドレスで、パスワードを間違えたときと、**まったく同じメッセージ**（「メールアドレスまたはパスワードが正しくありません。」）。

## 手順 6: 考える

- **正しいパスワードでも入れなくなること**: 制限は、**攻撃者を止める**ために働くが、同時に、**本物の利用者も、一時的に締め出す**。だから、制限の回数や時間は、**攻撃を防げて、かつ、利用者の不便が小さい**範囲で決める。また、他人に、わざと失敗を繰り返されて、**本物の利用者を締め出される**（嫌がらせ）恐れも、考慮する。
- **レート制限だけでは、防ぎきれない攻撃**: **たくさんの場所（IP アドレス）から、1 か所あたり、少ない回数ずつ試す**攻撃。1 か所ごとの回数が少ないので、制限に、かからない。また、**多数のアカウントに、よくあるパスワード 1 つ**を試す方法も、1 アカウントあたりの失敗が、少ない。
- **CAPTCHA（Turnstile など）の役割と流れ**:
  1. 画面に、ウィジェット（**公開されたサイトキー**を使う）が表示される。
  2. ブラウザが、**人間らしさを確かめた結果の、1 回限りのトークン**を受け取る。
  3. ログインのリクエストに、**そのトークンを添えて**、サーバーに送る。
  4. **サーバー（または、認証の仕組み）が、秘密の鍵で、トークンを検証**する。検証に通らなければ、ログインを処理しない。
  - これで、**機械的な大量の試行を、難しく、コストの高いもの**にできる。
  - **サーバー側で検証する理由**: 画面（ブラウザ）は、利用者のものなので、**「検証に通った」という画面の表示は、偽装できる**から。サーバーが、**秘密の鍵で、本物かどうかを確かめる**。
  - **完全ではない**ので、レート制限などと、**重ねる**。
- **存在しないメールアドレスでも、メッセージが同じ理由**: 「このメールアドレスは、登録されていません」と伝えると、攻撃者は、**どのメールアドレスのアカウントが存在するか**を、調べられる（列挙攻撃）。存在するアカウントが分かると、そこに絞って、パスワードを試せる。**教えすぎない**ことが、守りになる。

## 振り返りの答え

- **ブルートフォースとレート制限**: ブルートフォースは、パスワードを、**機械的に、何度も試す**攻撃。レート制限は、**短時間に失敗が続いたら、受け付けない**ことで、**1 か所からの総当たりを、現実的でなくする**。
- **ボット対策と、レート制限の役割の違い**: レート制限は、「**回数**」で止める（同じ相手からの、短時間の失敗）。ボット対策（Turnstile など）は、「**人間か、機械か**」を確かめて、**機械的な試行そのものを、難しくする**。**役割が違うので、重ねる**。

## 補足（この題材の限界）

- 失敗の記録は、**サーバーのメモリの上だけ**。再起動で消え、**複数台のサーバーでは共有されない**。実際のシステムでは、共有の保存先（データベースなど）や、認証の仕組みの機能を使う。
- 制限の単位は、**IP アドレス**。同じ会社や学校の、**多数の人が、同じ IP から**アクセスすると、**まとめて制限される**ことがある。
